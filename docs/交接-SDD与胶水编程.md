## 1. 这个仓库是什么

企业规格驱动的智能研发主库。阶段是：需求、概要设计、详细设计、程序设计、编码、测试设计、测试执行、分提。

- 进行中的规格在 `ai-agent/spec/{需求项编号}/`。子条目在 `spec/{需求项}/{子条目}/`，子条目编号以 `5` 开头。
- 已关闭规格进 `ai-agent/archive/YYMM/{需求项编号}/`。
- 业务代码写在点名的 `git-repo-*`（已检出的工作副本）或 `work/{需求项编号}/{目标库}/`（目标库未检出）。不写进 `ai-agent/` 或 `docs/`。
- 一次会话只做一个阶段。入口技能是 `ai-agent/skills/pipeline/sdd-flow-skill/skill.md`。
- 组织级规则在 `ai-agent/rules/工程规约.md`。各阶段还有公共规约和应用规约。应用规约的空表表示未知，必须问人，禁止把空表里的例子当成事实。

`agent-skills/` 是外部高星技能的本地参考，不要把那里的产物路径（`SPEC.md`、`ARCHITECTURE-SPINE.md`、`docs/ideas`、独立 ADR）写进本仓库流程。

## 2. 已经写进文件的流程

这些已经在规约、模板、技能和评估里，不要推倒重写。

| 阶段 | 进入条件 | 产物 |
|---|---|---|
| 需求 | 一句话诉求 | 需求用例。变更类型分业务需求、技术变更。必须有 P0。来源未知就问，不编造工单号 |
| 概要设计 | 需求确认通过 | 服务、调用方向、数据归属、失败与补偿。类和方法不在这里定 |
| 详细设计 | 同一份概要里架构师确认为通过 | 子条目契约：字段、状态、异常码、处理步骤。不写代码路径 |
| 程序设计 | 详细设计通过且无阻塞待确认 | 一个子条目一个目标库。方法失败对上异常码。P0 写明先失败的测试 |
| 编码 | 程序设计通过 | 在点名目录实现。有行为的类要有测试类；改动的对外方法要有成功和失败测试方法。P0 先失败再通过。不提交、不推送 |
| 测试设计 | 需求确认通过后即可，可与设计、编码并行 | 验收设计和用例。不写单元测试。优先级从用例继承，不把 P1 抬成 P0 |
| 测试执行 | 编码评估通过，且每个 P0 子条目的编码评估已过 | P0 执行结果。阻塞不算通过。单元测试通过不算验收通过 |
| 分提 | P0 有结果且失败项已关闭 | 按技能分提 |

变更类型按这个顺序判定，命中即停：

1. **技术变更**：依赖、运行时或构建升级，无新能力，对外可见行为不变。概要第 1 节写四件事：版本从哪到哪、行为变化写「无」、如何证明、如何回退。其余节写「不适用」。不为升版本新建业务测试类，跑程序设计点名的既有套件或构建。
2. **结构变更**：新服务、新的系统间调用、同步或异步变化、数据归属变化，或升级改变了返回、错误、时序、默认配置。对既有调用方标明兼容或破坏。破坏必须有取舍。服务不少于 2 个或系统级接口不少于 2 条时，概要在接口表后加 mermaid，只画调用方向。
3. **范围内改动**：只改已有服务，沿用既有调用，数据归属不变。可以跨多个服务和多个 `git-repo-*`。多库本身不构成结构变更。接口表写「沿用既有，无新增」。主流程仍经过的既有调用要写失败与补偿。

其他已经落地的规则：

- 需求确认人在需求应用规约；空则问。架构师确认在概要文档内。Agent 不能代签。确认通过只打开下一设计阶段，不打开编码。
- 范围、验收、优先级、影响服务一变，需求确认和架构师确认都回到待确认，旧的测试「通过」失效。详细设计的字段、状态、异常码或处理顺序一变，程序设计作废，编码停止。
- 图只用 mermaid，不另存图片。表和步骤是事实源。详细设计：有分支、循环或部分成功才画流程图；一个子条目按顺序调用多个已有模块且调用方能看见中间失败，才画时序图。方法级调用链在程序设计。
- 一个子条目只属于一个概要模块、一个服务、一个目标库。提供方拥有字段表，消费方只引用提供方子条目编号。P0 用例必须有子条目承接。
- 编码记录在 `spec/{需求项}/{子条目}/{子条目}_编码记录_{短标题}.md`。交付前两个技能并行：`code-review-skill` 看是否偏离设计，`code-quality-skill` 看代码质量。任一侧 Critical 未清零，不能进入测试执行。质量技能的上游检查单已归档在 `ai-agent/skills/coding/code-quality-skill/archive/`，不安装 `ocr`，也不建知识图谱。
- Java 单元测试：本次改动的每个有行为的类一个测试类，放在该模块 `src/test/java`、同包；仓库已有别的测试根就跟随仓库。每个改动的对外方法至少一条成功、一条失败。数据类不建测试类。不补未改动的旧方法，除非程序设计验证表点了名。
- 编码只改程序设计点名的目录。仓未检出就停，说明该克隆哪个库、哪个版本，不擅自克隆到别的路径。要改某个内部组件本身时，才把该组件仓检出为 `git-repo-*` 并走同一套阶段。

## 4. 已拍板、尚未写入规约

下面是聊天结论。`工程规约`、详细设计、程序设计、编码规约都还没有按此改过。下次若要落地，改这些现有文件，不新建技能，不把示例写进应用规约。

### 4.1 思想

规格管「做成什么」，物料管「用什么做成」。与现有阶段不冲突。需求、概要、详细设计、程序设计继续管意图和契约。编码在已经点名的组件、版本和样板里写最小胶水。

胶水编程交接稿在 `docs/胶水编程-最终版设计-for-Cursor.md`。它的核心思想可以吸收。它的运行流程（读规格、匹配、拉文档、改业务仓）只放在程序设计点名之后的编码，不能绕过需求确认、架构师确认、详细设计和程序设计。`.ai/tracks/`、Catalog 服务、IDEA 插件是提供方平台形态，不替换 `ai-agent/spec/`。稿里的 `panda-test`、`https://123.12.1.21`、`com.example.internal` 只是格式示例。

### 4.2 复用判定

- 需求阶段不选组件。概要设计不查文档库。拿不准是不是已有进程内组件时，概要写入待确认，不为此发明新服务或新的系统间调用。进程内组件不是新服务，也不是系统间接口。
- 详细设计按能力查组件目录。一条命中：处理步骤的完成方式写「既有组件」，依据写文档名和章节，组件名必须来自读到的那一页。同一能力多条命中：写成阻塞程序设计的待确认，一次只问用哪一个。零条命中：完成方式写「本服务实现」，依据写「无」。目录地址为空：停止并问，不能把「没查」写成「无」。
- 一个需求本来就要用多个不同能力时，可以各绑一个。禁止一次自动深拉多个候选再自行挑。
- 程序设计把「既有组件」绑定到组件 id、GAV、版本、文档地址、样板 tag，并只写相对样板的差异。公开方法来自该版本文档；文档没有签名时，只读该组件对应的公开类。要改公开签名就停。只改组件内部且公开方法不变：另开子条目，目标库换成组件仓。公开方法被破坏：按结构变更回到概要设计。
- 应用规约「必须复用」仍只放人已经写明、每次都要复用的方法。某一次查到的组件写在该子条目的程序设计里，不回填进这张空表。
- 编码不另选组件。写调用前必须阅读程序设计点名的那一节文档和那一版样板。顺序是：抄该版本样板，引入该 GAV，只写组件覆盖不了的胶水。单元测试只证明本服务在组件成功和失败时的行为，不给组件内部补测试类。点名组件被另外实现一套，设计符合审查为 Critical。
- 技术变更不按能力重新匹配组件。版本变化写在程序设计里，人确认后再编码。
- jar、该版本文档、该版本样板必须一起发布。样板测试不通过，该版本不能标成可抄。样板在提供方的 `references/<id>-ref`，不把业务仓里的旧调用当成组件样板。业务仓只用来对照本服务的分层。

常驻与按需：

- 常驻：工程规约、已填写的应用规约、`AGENTS.md` 红线、目录元数据。
- 按需：命中组件的那一版文档页和那一版样板。
- 禁止把组件文档库全文放进上下文，也禁止抄进本仓库 `docs/` 或使用方业务仓。

### 4.3 最优交付

三件发布物，使用方只做一次接入。不要收成一个插件整包。

| 发布物 | 谁维护 | 使用方仓库里有什么 |
|---|---|---|
| 流程包 | 按阶段门禁打版本 | 锁死的版本号。规约、技能、模板从这版读取 |
| 组件目录 | 组件发布时更新 | `glue.yaml` 里的目录地址和校验和。本地只有元数据，没有文档正文 |
| 组件三件套 | 每个组件同版本发布 | 业务仓不保存。编码时按程序设计点名的版本拉取 jar、文档、样板 |

`glue.yaml` 声明规格目录。本主库继续用 `ai-agent/spec/`。使用方业务仓默认用自己的 `spec/`，不把规格写进只读流程包。

第一期用初始化命令 `glue-init`，不先做 IDE 插件，也不先做 MCP。目录先是带校验和的 `index.yaml`。组件到五十个左右再按分类拆，不到需要服务化的规模不单做目录服务。门禁放在使用方流水线：新增依赖必须是目录中 `active` 或 `experimental` 的 GAV；废弃坐标不能进新代码。第一期绕过检测用规则，审计先记流水线日志。

实现顺序，前一步没有真实地址就不填假坐标：

1. 把第 4.2 节写进工程规约、概要公共规约、详细设计（公共规约、模板、评估、`detail-design-skill`）、程序设计（公共规约、模板、评估、`program-design-skill`）、编码公共规约和 `code-review-skill`。
2. 定目录条目字段：id、一句话能力、标签、GAV、文档路径模板、样板 tag、维护人、状态。正文留在文档库。
3. 做 `glue-init`：校验流程包和目录的校验和，写入 `glue.yaml` 和 `AGENTS.md`，失败回滚。
4. 用一个真实组件打通 jar、同版本文档、同版本样板 tag。
5. 接使用方流水线门禁。

使用方日常：一句需求进入需求阶段，一次只走一个阶段。详细设计才查目录。程序设计写明版本和样板后才编码。合入前流水线再用目录查依赖。
