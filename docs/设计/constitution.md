# 规格驱动与资产复用 Constitution

## Core Principles

### I. 规格决定做什么，材料决定用什么做

规格拥有“做什么”。材料拥有“用什么做”。二者不得互换。

- 需求 MUST NOT 选定组件。
- 概要设计 MUST NOT 读取文档库正文。只在写出新服务或新的系统间调用之前，读取目录元数据：id、一句话能力、tags、status。
- 详细设计决定完成方式。完成方式只允许「既有组件」或「本服务实现」。
- 程序设计锁定 id、GAV、版本、文档地址、样例 tag，以及相对样例的差异。
- 编码只复制该版本的样例、加入该 GAV，并只写组件未覆盖的胶水。
- 单测证明本服务在组件成功和失败时的行为。MUST NOT 把组件内部测试当作本服务的通过证据。
- 重写已点名组件，在代码评审中为 Critical。

理由：组件选型若提前到需求或概要正文，后续阶段无法区分“要做什么”和“碰巧用了哪一版”。

### II. 沿用既有阶段，不另建产品规格体系

产品阶段保持：需求、概要设计、详细设计、程序设计、编码、测试设计、测试执行、分提。一次会话只做一个阶段。

- 产品规格在进行中放在 `ai-agent/spec/{需求项}/`，关闭后放在 `ai-agent/archive/YYMM/`。
- MUST NOT 创建 `.ai/tracks/` 或 `.ai/constitution.md`。
- MUST NOT 把组件手册复制进 `docs/`。
- 本仓库用 Spec Kit 编写这次设计。`.specify/` 只服务这次编写。它 MUST NOT 成为交付给使用方的第二套产品规格目录。

理由：使用方已经按 `ai-agent/` 下的阶段规约工作。再给一套产品规格，阶段门禁会分裂。

### III. 未知事实必须留空

确认人、服务名、仓库、账号、命令、目录地址、文档库地址、Maven 坐标、组件名，凡仓库和对话里没有的，MUST 留空并向人询问。

- 空表表示未知。MUST NOT 用示例填成已确认事实。
- `panda-test`、`https://123.12.1.21`、`com.example.internal` 只说明格式。MUST NOT 把它们写成真实地址或坐标。
- 应用规约模板 MUST 逐字段说明：填什么、只填已经存在的事实、留空时哪一阶段问人、哪一阶段读取。
- 示例若需要，MUST 放在单独文件，并标明不得照抄。

理由：编造的地址和坐标会在后续规格、计划和实现里被当成可以调用的依赖。

### IV. 检索与决策分开

阶段技能决定何时检索、如何决策。MCP 只负责按版本读取。技能 MUST NOT 代替远程读取。

- MUST NOT 新增面向用户或内部的技能来做目录检索。目录规则写入工程规约，步骤写入既有阶段技能。
- 远程读取只有一个 MCP，服务名 `glue`。工具为 `search_components`、`get_component`、`get_doc_section`、`get_sample`。
- 工具契约写在 `ai-agent/mcp/glue.md`。服务进程、目录索引、jar、文档、样例和令牌留在提供方，MUST NOT 打进 harness。
- 使用方 IDE 配置把服务名 `glue` 指到提供方地址。令牌使用环境变量 `GLUE_TOKEN`，MUST NOT 提交到仓库。
- 地址缺失、调用失败或版本不一致时，MUST 停止并询问。
- 业务代码 MUST NOT 调用该 MCP。由代理在对应阶段调用。

理由：把检索写进技能或业务代码，阶段门禁可以被“帮我找个组件”绕开，版本也无法审计。

### V. 人确认，代理不签字

代理 MUST NOT 签署需求确认或架构师确认。

- 确认只打开下一设计阶段。确认本身不打开编码。
- 范围、验收、优先级或受影响服务发生变化时，两处确认都作废，已有测试“通过”作废。
- 详细设计的字段、状态、错误码或步骤顺序发生变化时，程序设计作废，编码停止。
- 漂移分类只由人确认类别。该确认不是需求确认，也不是架构师签字。

理由：代理签字会把未决问题写成已批准，后续阶段失去打回依据。

### VI. 交付可下载 harness，不进入使用方流水线

交付物是可下载的 harness。MUST NOT 要求使用方的合并或构建流水线运行 `glue-init --check` 或 `glue-gate`。

- 建议使用方不修改公共规约。不禁止修改。改过的副本不再是发布版本。
- MUST NOT 要求使用方用复制或目录替换去覆盖公共规约。
- 组件目录和组件三件套（jar、版本文档、样例）MUST NOT 放进 harness。
- 公司现有插件可以只作为安装入口。它 MUST NOT 作为规约正文的来源。

理由：提供方不能干涉使用方流水线。把门禁放进对方 CI，这套交付就无法落地。

### VII. 规格保鲜走既有打回

spec 保持事实来源。MUST NOT 用 git diff 回写 spec。MUST NOT 另建 Track。

已命名的写入目录已有改动时，继续编码前做漂移分类。交付前的设计符合性评审再做一次。只比较该写入目录和依赖文件。

- 仅代码漂移：改代码。
- 方法、目标库或组件版本变化：程序设计作废。
- 字段、状态、错误码或顺序变化：先回详细设计，程序设计作废。
- 范围、验收、优先级或服务变化：两处确认重置。
- 公共 API 被破坏：按结构变更回到概要设计。
- 无法判断：停止，只问一个问题。

理由：用 diff 改 spec 会让代码反过来定义需求。分类后打回原阶段，责任边界保持不变。

## 资产复用约束

变更类型按此顺序判断，命中即停：技术变更、结构变更、范围内改动。多仓库本身不是结构变更。进程内组件不是新服务，也不是系统间接口。

子项编号以 5 开头。一个子项对应一个概要模块、一个服务、一个目标库。

目录条目字段为：id、一句话能力、tags、GAV、文档路径模板、样例 tag、维护人、status。status 只允许 `active`、`experimental`、`deprecated`。`deprecated` 不是命中，除非需求明确保留该旧组件。

检索结果只允许四种处理：

- 恰好一个：记下候选 id，标记「待详细设计绑定」。这不是完成方式，也不锁定版本。
- 多个：阻塞，状态为待确认，一次只问一个。
- 零个：沿原变更类型继续。MUST NOT 编造组件。
- 调用失败、地址缺失或版本不一致：停住该新服务或新的系统间调用。范围内改动可以继续。

详细设计只搜索概要已经记录的候选 id。结果与概要矛盾时，回到概要。多种不同能力可以各绑定一个组件。MUST NOT 把多个候选深拉后自行挑选。

「既有组件」的证据是文档名和章节，组件名必须来自读到的页面。「本服务实现」的证据写「无」，并且只在真实零命中时允许。未查询 MUST NOT 写成「无」。

技术变更不按能力重新匹配。版本变更写在程序设计里，编码前由人确认。MUST NOT 自动跟随更新的版本。

公共签名变化时停止。仅内部变化且公共方法保持稳定：开新子项，目标库改为组件库。公共方法被破坏：按结构变更回到概要设计。

「必须复用」只收录人已经声明每次都必须复用的方法。一次目录命中写在该子项的程序设计中，MUST NOT 回写进空的应用规约表。把它提升为必须复用，是单独的治理修改。

代码只写在已点名的 `git-repo-*`。目标库未检出时，才写 `work/{需求项}/{目标库}/`。

`search_components` 在概要设计的返回只含 id、一句话能力、tags、status。`get_component` 用于详细设计和程序设计，返回八个目录字段，不含正文。`get_doc_section` 必须带 id、版本和章节，拒绝无版本请求和整站拉取。`get_sample` 只在编码使用，先给该版本的文件列表，再读文件。样例测试通过后，该版本才可以作为可复制版本返回。样例路径为 `references/<id>-ref`，tag 与版本对齐。

审计记录：时间、身份、工具、组件 id、版本、允许或拒绝、原因。

## 设计写作边界

这次 Spec Kit 规格只描述已经拍板的内容：harness 的文件与用法、`glue` 的工具契约、资产复用在既有阶段上的挂接、应用规约模板的填写说明。

- MUST NOT 把交接文档里的六条工作流当成一个新系统开工。
- MUST NOT 安装 ocr。MUST NOT 建立代码知识图谱。
- 规格、计划和任务里，尚未存在的目录地址、文档宿主、样例库、第一个组件和 MCP 地址 MUST 留空。
- 把句子写入工程规约、阶段技能、`ai-agent/mcp/glue.md` 和应用规约模板，属于后续计划和实现。本宪法不直接修改那些文件。

## Governance

本宪法高于同一次设计中与之冲突的说明。`docs/规格驱动与资产复用.md` 里仍要求使用方流水线核对校验和、或把过程包挂到 `.sdd/process/` 的段落，在与本宪法冲突时以本宪法为准，直到后续规格改写该文档。

产品运行时的阶段规则仍以 `ai-agent/rules/工程规约.md` 和既有阶段技能为准。本宪法不替代那些文件。

修订程序：

- 修改原则时写明变更原因，按下面的版本规则递增，并经人确认后才约束新的规格、计划和任务。
- MAJOR：删除原则，或把已有原则改成不能兼容的含义。
- MINOR：新增原则，或实质性加长约束。
- PATCH：澄清措辞，不改变约束。

合规检查：评审 `/speckit-specify`、`/speckit-plan`、`/speckit-tasks` 的产物时对照本宪法。出现新技能、使用方流水线门禁、Track、编造地址，或把 `.specify/` 写成产品规格目录，即不合规。
