# Feature Specification: 规格驱动与资产复用阶段包

**Feature Branch**: `001-asset-reuse-harness`

**Created**: 2026-10-12

**Status**: Draft

**Input**: User description: "按已拍板的章程，写出规格驱动与资产复用的完整设计：可下载阶段包如何让各开发组沿用现有阶段完成需求，资产查阅如何挂在既有阶段上，应用规约模板如何填写后即可使用。提供方不进入使用方流水线。尚未提供的地址、坐标、确认人和组件名保持空白。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 下载阶段包并填完应用侧规则 (Priority: P1)

开发组从提供方取得一份阶段包，放到自己的工程里，按现有八个阶段处理需求。公共规则保持为发布版本。应用侧规则按模板逐项填写已经存在的事实。未知项留空，到对应阶段再问人。提供方不修改开发组的合并或构建流水线。

**Why this priority**: 没有这份包，各开发组无法用同一套阶段规则开工。这是其余复用行为的前提，并且可以单独演示。

**Independent Test**: 取一份尚未填写应用侧规则的工程，放入阶段包，只填写模板中已经有事实的字段。完成一次范围内改动的需求交接，且开发组流水线保持原样。

**Acceptance Scenarios**:

1. **Given** 开发组还没有这套阶段规则，**When** 他们取得阶段包并按模板填写已有事实，**Then** 他们可以按需求、概要设计、详细设计、程序设计、编码、测试设计、测试执行、分提处理需求。
2. **Given** 某个应用侧字段没有事实，**When** 开发组对照模板，**Then** 该字段保持空白，模板写明哪一阶段必须问人、哪一阶段会读取它。
3. **Given** 开发组修改了公共规则，**When** 他们继续使用这份副本，**Then** 该副本不再视为提供方的发布版本，阶段包本身不因此阻止他们修改。
4. **Given** 开发组已经填过应用侧规则，**When** 他们再次取得阶段包，**Then** 已填写的内容仍在，不会被整包替换清掉。
5. **Given** 一次改动涉及多个代码库，**When** 判断变更类型，**Then** 仅因多个代码库不把它当成结构变更；进程内资产不把它当成新服务或系统间调用。

---

### User Story 2 - 新建能力时决定是否复用已有资产 (Priority: P2)

需求只描述要做什么。准备新建服务或新建系统间调用时，概要设计只按标识、一句话能力、标签和状态做分类。详细设计在这些候选里决定用既有资产还是本服务自己实现，并留下读到的证据。程序设计锁定版本。编码只补资产未覆盖的部分。

**Why this priority**: 复用的价值在于少写重复实现，同时不让选型提前污染需求，也不让未锁定的版本进入编码。

**Independent Test**: 用一条需要新建服务的需求走完概要、详细、程序和编码四步，核对每步留下的记录种类，不依赖开发组流水线。

**Acceptance Scenarios**:

1. **Given** 需求尚未进入设计，**When** 编写需求，**Then** 需求中不出现选定的可复用资产。
2. **Given** 概要设计准备写出一个新服务或一次新的系统间调用，且查阅恰好命中一个在用或试验资产，**When** 记录结果，**Then** 只记下候选标识并标为待详细设计绑定，不写完成方式，不锁版本，不摘录文档正文。
3. **Given** 同一次查阅命中多个资产，**When** 概要设计继续，**Then** 工作阻塞，一次只向人提一个问题。
4. **Given** 查阅结果为零，**When** 概要设计继续，**Then** 沿原来的变更类型往下做，不编造资产名称。
5. **Given** 查阅失败、查阅地址缺失或版本对不上，**When** 处理这次新服务或新的系统间调用，**Then** 该事项停止并询问。同一需求里的范围内改动仍可继续。
6. **Given** 概要只记录了一个候选，**When** 详细设计决定完成方式，**Then** 只在该候选上决定。写成既有资产时，能指出读到的文档名称和章节，资产名来自该页。写成本服务实现时，对应查阅确实为零命中。未查阅的能力不会被写成无。
7. **Given** 详细设计的结论与概要记录矛盾，**When** 发现矛盾，**Then** 回到概要设计，不在详细设计里改选别的资产。
8. **Given** 程序设计已经锁定标识、版本、文档位置、样例标记和与样例的差异，且该版本的样例自身测试已通过，**When** 编码，**Then** 只取该版本样例，只编写资产未覆盖的部分。验证要覆盖资产成功和资产失败两种情况。

### User Story 3 - 已有改动与规格不一致时打回 (Priority: P3)

规格仍是事实来源。准备继续编码时，若已命名的写入位置已经有改动，先由人判定漂移类别，再回到负责该类别的阶段。交付前的符合性评审再做一次。代理不替人签字。

**Why this priority**: 没有这条，代码会反过来改写需求，或者在确认被作废后仍然继续编码。

**Independent Test**: 在已有未分类改动的写入位置上请求继续编码，确认在人给出类别之前编码不开始；再分别用五类漂移核对打回去向。

**Acceptance Scenarios**:

1. **Given** 已命名的写入位置已有改动且尚未分类，**When** 请求继续编码，**Then** 编码不开始，直到人确认漂移类别。该确认不代替需求确认，也不代替架构师确认。
2. **Given** 人确认只是代码偏离规格，**When** 分类完成，**Then** 修正代码，规格保持不变。
3. **Given** 变化落在方法、目标工程或资产版本，**When** 分类完成，**Then** 程序设计作废，编码停止。
4. **Given** 变化落在字段、状态、错误码或步骤顺序，**When** 分类完成，**Then** 先回到详细设计，程序设计作废。
5. **Given** 变化落在范围、验收、优先级或受影响服务，**When** 分类完成，**Then** 需求确认和架构师确认都作废，已有测试通过作废。
6. **Given** 公共用法被破坏，**When** 分类完成，**Then** 按结构变更回到概要设计。
7. **Given** 无法判断类别，**When** 分类受阻，**Then** 停止，只问一个问题。

---

### User Story 4 - 把一次复用和每次必须复用分开 (Priority: P4)

某次需求用到一个资产，只记录在该子项的程序设计里。应用规约中的“每次必须复用”只收录人已经声明以后每次都要复用的用法。把一次命中提升为每次必须复用，是另一次治理修改。

**Why this priority**: 避免一次碰巧的选用被写成全组永久规则，也避免空表被自动填上。

**Independent Test**: 完成一次资产选用后，核对该子项程序设计有记录，应用规约中的必须复用清单与选用前一致。

**Acceptance Scenarios**:

1. **Given** 必须复用清单为空，且本次详细设计选用了一个资产，**When** 程序设计写完，**Then** 该子项记有这次选用，必须复用清单仍为空。
2. **Given** 人要把它定为以后每次都复用，**When** 做治理修改，**Then** 单独改应用规约，不借这次需求的程序设计自动回写。

---

### Edge Cases

- 资产状态为停用时，不算命中，除非本次需求明确要求保留该旧资产。
- 多种不同能力可以各自绑定一个资产。不得把多个候选都深入阅读后再自行挑一个。
- 技术变更不按能力重新匹配资产，也不自动改用更新的版本。版本变更写在程序设计中，编码前由人确认。
- 公共用法发生变化时停止。仅内部变化且公共用法保持不变时，另开子项，目标改为资产所在工程。
- 代理不得在需求确认栏或架构师确认栏签字。确认只打开下一设计阶段，不打开编码。
- 详细设计的字段、状态、错误码或步骤顺序在编码前发生变化时，程序设计作废，编码停止。
- 一次会话只处理一个阶段。
- 子项编号以 5 开头。一个子项只对应一个概要模块、一个服务、一个目标工程。
- 代码写在已经点名且已检出的目标代码库中。目标库尚未检出时，才放在规格库的暂存位置。
- 查阅文档时必须同时指定资产、版本和章节。没有版本，或一次取走全部文档，查阅被拒绝。
- 样例自身测试未通过的版本，不得作为可复制样例。样例标记与锁定的版本一致。
- 格式示例不得被当成真实地址、坐标或组件名填进模板。
- 重写已经点名的资产，在代码评审中为阻断级。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 提供方必须发布一份可下载的阶段包。开发组取得后，必须能沿用需求、概要设计、详细设计、程序设计、编码、测试设计、测试执行、分提处理需求。
- **FR-002**: 阶段包必须包含公共阶段规则、各阶段的执行说明，以及六份应用侧规则的空白模板。组件程序包、组件文档正文和样例不得放入阶段包。
- **FR-003**: 阶段包必须建议开发组保持公共规则为发布版本，同时允许开发组修改。修改后的副本不得再称为提供方的发布版本。
- **FR-004**: 再次取得阶段包时，必须保留开发组已经填写的应用侧规则，不得用整包替换把它们清掉。
- **FR-005**: 开发组的合并流水线和构建流水线不得被要求增加核对步骤。
- **FR-006**: 公司现有安装入口只负责把阶段包放到开发组工程中。规则正文必须以阶段包为准。
- **FR-007**: 六份应用侧模板的每个待填字段必须说明四件事：填写什么、只填写已经存在的事实、留空时哪一阶段问人、哪一阶段读取该字段。
- **FR-008**: 确认人、服务名、仓库、账号、命令、目录地址、文档位置、组件发布标识和组件名，在没有事实时必须保持空白，并在该阶段向人询问。
- **FR-009**: 格式示例必须与可填写模板分开，并标明不得照抄。已知的格式示例不得被写成真实地址或坐标。
- **FR-010**: 需求阶段不得选定可复用资产。
- **FR-011**: 概要设计只在准备写出新服务或新的系统间调用时查阅资产，且只能看到标识、一句话能力、标签和状态。不得读取文档正文，不得锁定版本，不得写下完成方式。
- **FR-012**: 状态为停用的资产不得算作命中，除非本次需求明确保留该旧资产。
- **FR-013**: 恰好一个命中时，概要设计必须只记录候选标识，并标记为待详细设计绑定。
- **FR-014**: 多个命中时，工作必须阻塞，并且一次只向人提一个问题。
- **FR-015**: 零个命中时，必须沿原来的变更类型继续，不得编造资产。
- **FR-016**: 查阅失败、地址缺失或版本不一致时，必须停住该新服务或该新的系统间调用并询问。同一需求中的范围内改动可以继续。
- **FR-017**: 详细设计只能在概要已经记录的候选上决定完成方式。结论与概要矛盾时，必须回到概要设计。
- **FR-018**: 完成方式只允许两种：既有资产，或本服务实现。
- **FR-019**: 既有资产必须带有读到的文档名称和章节，资产名必须来自该页。本服务实现只允许出现在真实零命中之后，证据为无。未查阅不得写成无。
- **FR-020**: 多种不同能力可以各自绑定一个资产。不得深入阅读多个候选后再自行挑选。
- **FR-021**: 程序设计必须锁定本次使用的标识、版本、文档位置、样例标记，以及相对样例的差异。版本在编码前必须由人确认。不得自动改用更新的版本。
- **FR-022**: 编码只能复制已经通过自身测试的那个版本的样例，并且只编写该资产未覆盖的部分。
- **FR-023**: 对本服务的验证必须覆盖资产成功和资产失败两种情况。资产内部的测试不得作为本服务通过的证据。
- **FR-024**: 重写已经点名的资产，必须在代码评审中视为阻断级。
- **FR-025**: 技术变更不得按能力重新匹配资产。
- **FR-026**: 公共用法发生变化时必须停止。仅内部变化且公共用法不变时，必须另开子项，并把目标改为资产所在工程。公共用法被破坏时，必须按结构变更回到概要设计。
- **FR-027**: “每次必须复用”只收录人已经声明每次都要复用的用法。一次命中只记录在该子项的程序设计中，不得回写进空白的应用规约。提升为每次必须复用必须是单独的治理修改。
- **FR-028**: 代理不得签署需求确认或架构师确认。确认只打开下一设计阶段，不得据此开始编码。
- **FR-029**: 范围、验收、优先级或受影响服务发生变化时，两处确认都必须作废，已有测试通过必须作废。
- **FR-030**: 详细设计的字段、状态、错误码或步骤顺序发生变化时，程序设计必须作废，编码必须停止。
- **FR-031**: 已命名的写入位置已有改动时，继续编码前必须先做漂移分类。交付前的符合性评审必须再做一次。比较范围只包括该写入位置和依赖声明。
- **FR-032**: 漂移类别必须由人确认。该确认不是需求确认，也不是架构师确认。仅代码偏离则改代码；方法、目标工程或资产版本变化则程序设计作废；字段、状态、错误码或顺序变化则先回详细设计且程序设计作废；范围、验收、优先级或服务变化则两处确认重置；公共用法被破坏则回到概要设计；无法判断则停止并只问一个问题。
- **FR-033**: 规格必须保持事实来源。不得根据代码差异回写规格，不得另建一套规格同步轨迹。
- **FR-034**: 一次会话只能处理一个阶段。
- **FR-035**: 变更类型必须按技术变更、结构变更、范围内改动的顺序判断，命中即停。多个代码库本身不得构成结构变更。进程内资产不得被当成新服务或系统间调用。
- **FR-036**: 子项编号必须以 5 开头。一个子项只能对应一个概要模块、一个服务、一个目标工程。
- **FR-037**: 代码必须写在已经点名且已检出的目标代码库中。目标库尚未检出时，才允许放在规格库的暂存位置。
- **FR-038**: 资产查阅必须由提供方托管。开发组的业务代码不得直接查阅。每次查阅必须留下审计：时间、身份、查阅动作、资产标识、版本、允许或拒绝、原因。
- **FR-039**: 查阅文档时必须同时给出资产、版本和章节。没有版本的查阅和取走全部文档的查阅必须被拒绝。详细设计和程序设计读取资产登记时，必须能看到登记的全部字段，且不得包含文档正文。
- **FR-040**: 可复制样例的标记必须与锁定版本一致。该版本自身测试未通过时，不得作为可复制样例提供。
- **FR-041**: 不得新增单独的资产查找说明。查找时机和决策必须写进现有阶段说明，共用规则必须写进工程级规则。
- **FR-042**: 本次不得把交接材料中的六条工作流做成新系统，不得交付文字识别，不得交付代码知识图谱。
- **FR-043**: 阶段包、本规格和后续计划中，尚未提供的目录地址、文档宿主、样例库、第一个资产和查阅地址必须保持空白。

### Key Entities

- **阶段包**: 提供方发布、开发组下载后使用的一套阶段规则。包含公共规则、阶段执行说明和应用侧空白模板。不包含组件程序包、文档正文和样例。
- **公共规则**: 发布版本中的阶段规则。建议保持不改。改过的副本不再是发布版本。
- **应用侧规则**: 开发组按模板填写的本工程事实。六份分别对应需求、概要设计、详细设计、程序设计、编码、测试。再次取得阶段包时保留已填内容。
- **可复用资产**: 一条目录登记。字段为标识、一句话能力、标签、发布标识、文档位置模板、样例标记、维护人、状态。状态只允许在用（active）、试验（experimental）、停用（deprecated）。
- **候选绑定**: 概要设计在恰好一个命中时留下的标识，标记为待详细设计绑定。它不是完成方式，也不含版本。
- **完成方式**: 详细设计的决定，只为既有资产或本服务实现。既有资产要有文档名和章节。
- **版本锁定**: 程序设计对一次使用写下的标识、版本、文档位置、样例标记和与样例的差异。编码前由人确认。
- **子项**: 编号以 5 开头的工作单元。对应一个概要模块、一个服务、一个目标工程。
- **确认**: 需求确认或架构师确认，只能由人签署。另有漂移类别确认，不代替前两种。
- **漂移类别**: 人对已有改动的分类，决定回到改代码、程序设计、详细设计、两处确认或概要设计。
- **查阅审计**: 一次资产查阅的时间、身份、动作、资产标识、版本、允许或拒绝、原因。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 开发组不修改自己的合并或构建流水线，就能用阶段包把一次范围内改动从需求交到下一设计阶段。
- **SC-002**: 六份应用侧模板中，每个待填字段都同时具备填写说明、空白时的询问阶段和读取阶段。缺任何一项即判定该模板未完成。
- **SC-003**: 抽查新服务或新的系统间调用的概要记录时，100% 只属于三种结果之一：待绑定的单一候选、一次只提一个问题的待确认、或零命中后的原路径。这些记录中不出现版本和完成方式。
- **SC-004**: 抽查写有完成方式的详细设计时，100% 的“既有资产”能指出文档名和章节，100% 的“本服务实现”能对应到一次零命中查阅。
- **SC-005**: 人签字之前，代理产出的需求确认栏和架构师确认栏保持空白。抽查通过率为 100%。
- **SC-006**: 发布的阶段包中，组件程序包、组件文档正文和样例文件的数量为 0。
- **SC-007**: 完成一次资产选用后，应用侧“每次必须复用”清单与选用前相比，条目数不变。
- **SC-008**: 写入位置已有改动且人尚未确认漂移类别时，继续编码的次数为 0。

## Assumptions

- 使用本规格的读者是提供方和各开发组的负责人。阶段名称沿用他们已有的八个阶段，不另起一套流程。
- 一次会话只做一个阶段、子项以 5 开头、确认不打开编码，这些是已经落地的阶段规则。本规格把资产复用挂上去，不改阶段顺序。
- 资产查阅由提供方托管，开发组业务代码不直接查阅。查阅服务的名称、动作清单和契约位置以章程 1.0.0 为准，在计划中写明，不在本规格里重新选择。
- 章程 1.0.0 高于 `docs/规格驱动与资产复用.md` 里仍要求开发组流水线做校验、或把过程材料挂到另一套只读目录的段落。
- 目录地址、文档宿主、样例库、第一个资产、查阅地址、确认人、服务名和仓库名目前都没有事实，因此保持空白，不设默认值。
- `panda-test`、`https://123.12.1.21`、`com.example.internal` 只是既有材料里的格式示例。
- 公司现有安装入口可以继续负责放置阶段包。它不提供规则正文。
- 本次不创建 git 分支。功能目录名为 `specs/001-asset-reuse-harness`。`.specify/` 只用于编写这次设计，不交给开发组当作产品规格目录。
- 把规则写入工程级规则、现有阶段说明、查阅契约和应用侧模板，属于后续计划与实现，不属于本规格的交付物。
