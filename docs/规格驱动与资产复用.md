# 规格驱动与资产复用

日期：2026-10-12。

这是给人和智能体讲清楚用的设计说明。阶段门禁、变更类型、确认和打回，仍以仓库里已经写好的规约为准。资产复用按本文执行。本文里的查询、绑定、接入命令和依赖门禁，多数还没有写进 `工程规约.md` 和各阶段技能。文档库地址、样板仓、组件坐标都还未知。未知就问，不编造。

对照图：`.archify/workflow-sdd-glue-20261012-151000/sdd-glue-flow.html`。图只标阶段和资产，规则以本文为准。

## 1. 三句话

规格管做成什么。物料管用什么做成。两条线只在详细设计交汇一次：那里决定这项能力是用既有组件，还是由本服务自己实现。

选定之后不能再选。程序设计把选定的组件锁成一个版本和一套样板。编码只抄这一版，只写组件覆盖不了的胶水。合入前，流水线再核对新依赖是不是目录里允许的坐标。

开发组日常只做一个动作：说一句需求，然后一次只走一个阶段。不另开一条「找到组件就写代码」的旁路。

## 2. 两方各拿什么

提供方维护三样东西，使用方不改它们的正文。

| 发布物 | 里面有什么 | 使用方仓库里留下什么 |
|---|---|---|
| 流程包 | 工程规约、各阶段公共规约、现有技能、模板、评估、`AGENTS.md` 红线 | 一个锁死的版本号。智能体从这一版读取 |
| 组件目录 | 每条组件的元数据，外加整份目录的校验和 | `glue.yaml` 里的目录地址和校验和。可以有本地元数据副本，没有文档正文 |
| 组件三件套 | 同一版本的 jar、该版本的文档、该版本的样板 | 不预装。编码时按程序设计点名的版本拉取 |

使用方仓库里由本组维护、提供方升级时不得覆盖的，是这些：

- `glue.yaml`：流程包版本、目录地址、目录校验和、规格目录位置。
- 薄的 `AGENTS.md`：红线和「去读哪一版流程包」。
- 六份应用规约，以及 `docs/应用架构.md`、`docs/技术架构.md` 这类按应用填写的文档。
- 本组的 `spec/`。本主库继续用 `ai-agent/spec/`。别的开发组用自己仓库里的 `spec/`。
- 业务代码。仓已检出就写 `git-repo-*`，未检出就写 `work/{需求项编号}/{目标库}/`。

规格不写进流程包。流程包是只读的。各组把流程包拷出去改一版，就离开了统一门禁。每个文件的职责、接入后的目录、以及使用步骤见第 12 节和第 13 节。和插件、整包的差别见第 14 节。

## 3. 五层资产

越靠前越稳定，越靠后越按需。智能体不能把后面几层的正文提前灌进上下文。

| 层 | 是什么 | 谁维护 | 哪一阶段可以读 |
|---|---|---|---|
| 架构资产 | 应用架构、技术架构、数据架构、功能模块 | 应用自己填写 | 概要必读应用架构。服务名映射不上就待确认 |
| 规约资产 | 工程规约、已填写的应用规约、`AGENTS.md` 红线 | 流程包加本组填写的应用规约 | 每个阶段都读。空表表示未知 |
| 规格资产 | 进行中的 `spec/`，以及已关闭的 `archive/` | 需求流程 | 详细设计先查已有提供方子条目。有则引用编号，不复制字段表 |
| 组件目录 | id、一句话能力、标签、GAV、文档路径模板、样板 tag、维护人、状态 | 组件发布时更新 | 概要在特定条件下只读四个字段。详细设计按能力查询。程序设计才使用 GAV 和样板 tag |
| 组件三件套 | 某一版的 jar、文档、样板 | 组件负责人，三个必须同版本 | 只有程序设计写明版本之后，编码才拉那一版 |

目录是发现面，不是文档库。文档站、样板仓、本仓库 `docs/`、业务仓里的旧调用，都不是这次查询的来源。

状态只有三个：`active`、`experimental`、`deprecated`。概要和详细设计只把前两个算作命中。`deprecated` 不参与选型，除非这句需求明确要求留在旧组件上。废弃组件不能被新代码依赖。

jar、该版本文档、该版本样板一起发布。样板放在提供方的 `references/<id>-ref`。样板测试不通过，这一版不能标成可抄，也不能标成 `active`。业务仓里已经有人调用过，不能反过来当成样板。

## 4. 接入只做一次

各组在仓库根目录执行一次 `glue-init`。命令只认参数，不认对话里的口头地址。真实的流程包地址、目录地址、MCP 地址由发布时的参数传入。参数空着就失败退出，不写假地址。

```text
glue-init
  --process-version <版本>
  --process-url <流程包地址>
  --catalog-url <目录地址>
  --catalog-checksum <目录 SHA-256>
  --mcp-url <MCP 地址>
  --spec-dir spec
  --local-dir .sdd/local
```

本主库接入时 `--spec-dir` 用 `ai-agent/spec`。其他开发组用 `spec`。

命令按这个顺序做，每一步先记入本次新建文件清单，失败则只删除这份清单里的文件：

1. 下载该版本流程包，对照包内 `MANIFEST.yaml` 逐文件计算 SHA-256。任一文件不符就停止。
2. 把流程包展开到 `.sdd/process/`。这个目录只读。组内不改。
3. 下载目录的 `index.yaml` 到 `.sdd/catalog/index.yaml`，核对 `--catalog-checksum`。不符就停止。这里只有元数据，没有文档正文。
4. 写入仓库根的 `glue.yaml`。字段见第 12 节。
5. 用流程包里的 `AGENTS.template.md` 渲染仓库根的 `AGENTS.md`。内容只有红线、流程包版本、规格目录、以及「目录和文档只通过 MCP 读」。
6. 把 `templates/` 里的应用规约和架构文档模板复制到 `--local-dir`。目标文件已存在则跳过，不覆盖。
7. 写入 `.cursor/mcp.json` 里的 `glue` 一项。URL 来自 `--mcp-url`。令牌用环境变量 `GLUE_TOKEN`，不写进文件。

`--check` 不下载新文件。它重算 `.sdd/process/` 和 `.sdd/catalog/index.yaml` 的 SHA-256，并与 `glue.yaml` 比较。不一致则退出码非 0。使用方流水线在装依赖之前先跑这一步。

这一步不填写确认人、服务名、目标库、账号和 Maven 坐标。模板里的空表仍然是空的。

升级流程包是再执行一次 `glue-init` 并换 `--process-version`。`.sdd/local/` 里已有文件保持不动。已经在途的需求继续用开工时锁住的版本，直到人决定换版。

## 5. 一句需求怎么走完

下面按一次真实工作的顺序写。一次会话只推进到当前阶段的完成定义。测试设计在需求确认通过后就可以做，可与设计、编码并行；它不选组件，也不写单元测试。

讲述时不要把下面任何名字当成仓库里的真实服务或真实组件。应用架构和应用规约目前是空的。

### 5.1 入口

开发组说一句诉求。`sdd-flow` 读锁定的那一版流程包，查看 `spec/{需求项编号}/` 里已有文档和评估结论，只打开允许进入的那一个阶段。

没有需求项编号就停，向人要编号。不创建规格，不写代码。

### 5.2 需求

需求阶段回答做成什么：范围、验收、优先级、影响服务。必须有 P0。来源未知就问，不编造工单号。

这一阶段不选组件，也不查目录。诉求本身就是升级某个已有依赖、并且对外行为不变时，按技术变更写。组件是哪一个，以人的原话为准，不从目录里匹配一个出来。

确认人写在需求应用规约里。空着就向人要。智能体不能自己签字。确认通过只打开概要设计，不打开编码。

### 5.3 概要设计

概要回答落在哪、谁调用谁、失败谁负责。它不写字段、类和方法，也不写 GAV。

服务名只能来自 `docs/应用架构.md` 里已经有的服务。映射不上就待确认，不发明服务名。

这里新增一条查询，而且只在一种情况下做：准备写成「新服务」或「新的系统间调用」之前。查询对象是组件目录，不是文档正文。只读四个字段：

| 字段 | 用来判断什么 |
|---|---|
| id | 恰好命中一条时，记成候选 |
| 一句话能力 | 是不是同一项进程内能力 |
| 标签 | 同上 |
| 状态 | `active` 和 `experimental` 算命中 |

GAV、文档路径、样板 tag、维护人留在同一条目录记录里，概要不读，也不写进概要文档。

四种结果：

- 恰好一条：在模块上记下候选 id，标明「待详细设计绑定」。这里还不写完成方式，也不写版本。
- 多条：写成待确认，一次只问用哪一个。不问完，不能进入详细设计。
- 零条：按原来的变更类型继续。不发明一个组件，也不因为没查到就新建服务。
- 目录地址为空，或校验和不符：这条「新服务」或「新的系统间调用」停住，向人要可用的目录。范围内改动、沿用既有调用的，概要可以继续写，到详细设计再查目录。

进程内组件不是新服务，也不是系统间接口。架构师确认的是服务边界和调用方向。确认通过只打开详细设计。

### 5.4 详细设计

详细设计回答契约长什么样：字段、状态、异常码、处理步骤。它不写类名、方法名和代码路径。

这一阶段做两种复用。

规格复用：先查本需求项和 `archive/` 里是否已经有提供方子条目。有，就引用它的编号和字段，不复制整张表。没有，才新写字段表。一个子条目仍然只属于一个概要模块、一个服务、一个目标库。

组件复用：按这项能力查目录。概要若已经记下候选 id，只在这些候选里绑定，不另外再搜一遍。查询结果和概要的判断相反时，打回概要，不在详细设计里改服务边界。

处理步骤的完成方式只写两种之一：

- 「既有组件」。依据写读到的文档名和章节。组件名必须来自读到的那一页，不能凭记忆写。
- 「本服务实现」。依据写「无」。只有真正零条命中才能这样写。

同一项能力多条命中：写成阻塞程序设计的待确认，一次只问一个。目录没查：停止并问。没查不能写成「无」。

一个需求本来就要用多项不同能力时，可以各自绑定一个组件。禁止一次拉下多个候选的文档再自己挑。

技术变更不在这里按能力重新匹配组件。

### 5.5 程序设计

程序设计回答代码落在哪、方法怎么接上契约、先证明哪一条。一个子条目一个目标库。方法的失败必须对上详细设计的异常码。每个 P0 写明先写什么样的失败测试。

完成方式是「既有组件」时，程序设计把它写成一条拆不开的记录：

- 组件 id
- GAV
- 版本
- 文档地址
- 样板 tag
- 相对该样板要改的差异

公开方法以该版本文档为准。文档里没有方法签名时，只读该组件这个版本对应的公开类。要改公开签名就停。只改组件内部、公开方法不变：另开子条目，目标库换成组件仓，仍走同一套阶段。公开方法被破坏：按结构变更回到概要设计。

应用规约里人已经写明、每次都要复用的公共方法，照旧复用。某一次从目录查到的组件写在这份程序设计里，不回填进应用规约的「必须复用」。

技术变更的版本变化也写在程序设计里，人确认后再编码。编码不自动跟提供方后来发布的更新版本。

目标库不在应用规约里就问人，不自造库名。

### 5.6 编码之前先看有没有偏离

程序设计已经通过，并且它点名的写入目录里已经有改动：先做偏离分类，再决定能不能写。目录是干净的，或者还没开始写：直接编码。同一次会话中途不重复分类。

比较范围只有两处：点名写入目录里的改动，以及依赖文件。别的需求、别的库、纯格式化，不拿来改规格。判不准就停，只问一个问题。

人在这一步确认的是类别。这个确认不能代替需求确认人，也不能代替架构师。确认之后走第 8 节的打回。这一步不根据 `git diff` 改写规格。

### 5.7 编码

编码只消费程序设计那条绑定。顺序固定：

1. 读点名的那一节文档，和那一版样板。
2. 抄该版本样板里该抄的调用。
3. 引入该 GAV。
4. 只写组件覆盖不了的胶水。

写调用之前没有读到这节文档和这版样板，就不能写。jar、文档、样板的版本不一致，就停。

单元测试只证明本服务在组件成功和失败时的行为。不给组件内部补测试类。点名组件被另外实现一套，设计符合审查定为 Critical。

技术变更不新建业务测试类。跑程序设计点名的既有套件或构建。

编码不提交、不推送，除非当次明确要求。

### 5.8 交付前再分类一次

设计符合审查和质量审查仍然并行。两边的 Critical 都清零，才能进入测试执行。

设计符合审查使用和第 5.6 节同一份类别。前一次避免沿错误方向继续写，这一次接住本次会话里新产生的偏离。

### 5.9 测试执行

测试执行证明的是需求验收。编码记录里的单元测试通过，不算 P0 验收通过。样板自己的测试通过，也不算验收通过。

P0 有结果，失败项关闭，才能分提。阻塞不算通过。

### 5.10 分提和依赖门禁

分提仍按现有技能：每个代码库提交到各自远程。`work/` 里的改动在分提时再放到目标库。

使用方流水线在合入前做依赖门禁。新增依赖必须是目录中 `active` 或 `experimental` 的 GAV。废弃坐标不能进新代码。拒绝时给出建议的 GAV 和文档地址。审计从第一天就记入流水线日志：谁、何时、哪个组件、哪一版、允许还是拒绝。检测手段可以先用规则，拒绝和审计的格式不变。

## 6. 应用规约

应用规约写这个应用里每次做需求都成立的事实。确认人、编号从哪取、服务对应哪个库、每次都必须调用的公共方法、验证命令、测试环境，都属于这里。

一次需求里才出现的字段、异常码、组件和版本，写在该需求的规格里。只有这组人认定「以后每条需求都这样」，才补进应用规约。智能体不填这些表，`glue-init` 也不填。

空着是合法的。空着表示还不知道。走到那一阶段就向人问这一项。问到的答案先写进当前规格。

开发组接入时写下已经知道的项。不必六份填满才能开工。某一阶段开工前，只看这一阶段那一份：写明的直接沿用，没写明的当场问。

六份分别是：需求、概要设计、详细设计、程序设计、编码、测试。服务名以 `docs/应用架构.md` 为准。同一服务的目标库在程序设计应用规约和编码应用规约里写成同一行。验证命令只写在编码应用规约。

## 7. 规格保鲜

规格是事实源。代码和规格不一致时，先判定差异属于哪一层，再打开拥有该事实的那一阶段。不把 `git diff` 写回一份总规格，也不另做 Track。

| 看到的差异 | 接着做什么 |
|---|---|
| 代码偏离，范围、验收、字段、异常码、处理顺序、方法契约都没变 | 改回代码，留在编码 |
| 方法、目标库或组件版本变了 | 程序设计作废，编码停止，改完并重新评估再写 |
| 字段、状态、异常码或处理顺序变了 | 先改详细设计，程序设计作废 |
| 范围、验收、优先级或影响服务变了 | 需求确认和架构师确认回到待确认，旧的测试「通过」失效 |
| 组件公开方法被破坏 | 按结构变更回到概要设计 |

提供方后来发布了更新的组件版本，在途需求不自动升级。要升版就改程序设计，人确认后再编码。

## 8. 变更类型仍然先判定

资产复用不改变原来的判定顺序。命中即停。

1. 技术变更：依赖、运行时或构建升级，无新能力，对外可见行为不变。不按能力重新匹配组件。版本写在程序设计里。不为升版本新建业务测试类。
2. 结构变更：新服务、新的系统间调用、同步或异步变化、数据归属变化，或升级改变了返回、错误、时序、默认配置。写「新服务」或「新的系统间调用」之前，先做第 5.3 节的目录查询。
3. 范围内改动：只改已有服务，沿用既有调用，数据归属不变。可以跨多个库。多库本身不是结构变更。接口表写「沿用既有，无新增」。详细设计仍然可以按能力查目录。

## 9. 技能、MCP 和插件

这是最终方案，不再分成「先做命令、以后再做 MCP」。

开发组面对的入口仍然只有 `sdd-flow`。不新增目录技能、拉取技能、偏离分类技能，也不做 IDE 插件，也不做 DSH 插件。目录、文档和样板的远程读取只走一个 MCP。阶段规则只从已经锁定的流程包在本地读取。

### 9.1 技能改现有文件

共用的目录字段、四种查询结果、哪个阶段许读哪些字段，写进 `工程规约.md`。各技能只增加自己的那一步，并写明调用哪一个 MCP 工具。技能描述里写上「只在本阶段技能已经打开时执行」，避免一句「找个组件」直接命中。

| 技能文件 | 增加的实现 |
|---|---|
| `sdd-flow-skill/skill.md` | 进入编码前，若程序设计已通过且点名目录已有改动，先按第 7 节分类。目录干净则打开编码 |
| `outline-design-skill/skill.md` | 写出新服务或新的系统间调用之前，调用 `search_components`。只采用返回里的 id、一句话能力、标签、状态 |
| `detail-design-skill/skill.md` | 调用 `search_components` 或 `get_component`。已有候选 id 时只查这些 id。命中后调用 `get_doc_section` 核对组件名和章节，再写完成方式 |
| `program-design-skill/skill.md` | 调用 `get_component`，把 id、GAV、版本、文档地址、样板 tag 写入程序设计。不拉取样板正文 |
| `test-driven-skill/skill.md` | 写调用前调用 `get_doc_section` 和 `get_sample`，版本必须与程序设计一致。然后抄样板、引 GAV、写胶水 |
| `code-review-skill/skill.md` | 交付前用第 7 节再分类一次。点名组件被另写一套，定为 Critical |

`code-quality-skill` 仍只看代码质量，不查目录。`acceptance-trace-skill` 和 `split-submit-skill` 不选组件。

仓库里现在的 `agent.md` 把规格路径写成 `ai-agent/spec/`。打进流程包时改成读 `glue.yaml` 的 `specDir` 和 `process.path`。本主库的 `specDir` 仍是 `ai-agent/spec`。

### 9.2 MCP 是目录和文档的唯一远程读口

MCP 服务名 `glue`。它不回答「下一阶段是什么」，也不返回规约正文。规约在本地流程包里。MCP 中断时，新的目录查询和文档拉取停止；已经锁定的阶段规则照常生效，不能改走别的网址或业务仓。

四个工具：

| 工具 | 谁可以调用 | 入参 | 返回 |
|---|---|---|---|
| `search_components` | 概要、详细设计 | 能力关键词；可选的候选 id 列表 | 元数据列表。概要调用时服务端只回 id、一句话能力、标签、状态 |
| `get_component` | 详细设计、程序设计 | 组件 id | 该条的八个字段和推荐版本。不含文档正文 |
| `get_doc_section` | 详细设计、编码 | id、版本、章节 | 这一版这一节的正文。拒绝「不带版本」和「整站」 |
| `get_sample` | 编码 | id、版本 | 该版本样板的位置和文件清单。按文件再读。不返回其他版本 |

每次调用写一条审计：时间、调用身份、工具名、组件 id、版本、允许或拒绝、原因。身份来自 `GLUE_TOKEN` 对应的团队或流水线账号。令牌不进仓库、不进样板、不进流程包。

服务端用发布好的 `index.yaml` 做发现。组件不到需要拆分的规模时，不另做一套目录服务。MCP 是这份额数据的读口，不是第二份目录。

### 9.3 不提供插件

最终交付里没有 IDE 插件，也没有 DSH 插件。接入、检查锁定、调用 MCP，都由 `glue-init`、`glue.yaml`、`AGENTS.md` 和 `.cursor/mcp.json` 完成。流水线调用同一个 `glue-init --check`，以及同一个目录规则的 `glue-gate`。

`glue-gate` 读取本次变更里新增的依赖坐标，对照 `.sdd/catalog/index.yaml`。不在 `active` 或 `experimental` 中的新依赖，退出码非 0，并打印建议 GAV。它不读取业务源码来重新选择组件。

仓库里已经能照着走的，是规格驱动本身：八个阶段的门禁、变更类型、确认与打回、一次只做一阶段、空的应用规约必须问人、代码只写进点名目录。

### 12.2 组件目录

提供方发布一个 `index.yaml`。使用方只在 `.sdd/catalog/index.yaml` 保留这一份元数据副本和它的 SHA-256。

每条组件八个字段：id、一句话能力、标签、GAV、文档路径模板、样板 tag、维护人、状态。状态是 `active`、`experimental`、`deprecated`。正文不在这个文件里。

### 12.3 组件三件套

每个组件的每个可抄版本一起发布三样，缺一不能标 `active`：

| 发布物 | 做什么 |
|---|---|
| jar | 放在私有 Maven。编码只引入程序设计写明的那一个 GAV |
| 该版本文档 | 按版本和章节存放。`get_doc_section` 只返回点名的那一节 |
| 该版本样板 | 在提供方的 `references/<id>-ref`，tag 与版本对齐。`get_sample` 按这个 tag 给出文件清单 |

样板里至少有能单独构建的构建文件、一处标准调用、一个测试、以及绑定 id 和版本的元数据。样板测试不通过，这一版不能标成可抄。

| 路径 | 谁写 | 做什么 |
|---|---|---|
| `glue.yaml` | `glue-init` | 流程包版本和 SHA-256、目录地址和 SHA-256、MCP 地址、`specDir`、`localDir` |

| `.cursor/mcp.json` | `glue-init` | 登记 MCP 服务 `glue`。只有 URL。令牌在环境变量 `GLUE_TOKEN` |
| `.sdd/process/` | `glue-init` | 该版本流程包。只读 |
| `.sdd/catalog/index.yaml` | `glue-init` | 目录元数据副本 |
| `.sdd/local/` | 第一次复制模板，之后由人填 | 六份应用规约和架构文档 |
| `spec/` | 各阶段智能体 | 进行中的规格。本主库是 `ai-agent/spec/` |

```yaml

process:
  version: ""
  url: ""
  path: .sdd/process
  checksum: ""

  url: ""
  path: .sdd/catalog/index.yaml
  checksum: ""

  url: ""
```

## 13. 使用方怎么用

第一次，由本组的人在仓库根执行第 4 节的 `glue-init`。然后人填写 `.sdd/local/` 里已经知道的应用规约和 `docs/应用架构.md`。不知道的保持空白。

之后每次做需求：

1. 在智能体里说一句诉求。智能体先读仓库根 `AGENTS.md`，再读 `.sdd/process/` 里的 `sdd-flow-skill`。
2. `sdd-flow` 只打开当前阶段的 `agent.md`、该阶段公共规约、以及 `.sdd/local/` 里对应的那一份应用规约。
3. 概要或详细设计需要目录时，只调用 MCP `glue`。不打开文档站首页，不在业务仓里搜旧调用来代替目录。
4. 程序设计把版本和样板 tag 写进 `spec/` 的该子条目。编码按这两个值调用 `get_doc_section` 和 `get_sample`。
5. 代码写进程序设计点名的 `git-repo-*` 或 `work/`。
6. 交付前跑设计符合审查和质量审查。人要合入时，流水线先跑 `glue-init --check`，再跑 `glue-gate`。

人不要自己点技能名。不要把 `.sdd/process/` 里的文件改掉来「临时通一下」。要改门禁，改的是提供方的下一版流程包，然后由人决定这个仓库是否换版。

## 14. 为什么是这种交付，而不是插件或一个整包

这种交付把「规则文本」「目录元数据」「某一版的 jar、文档、样板」分成三件，用 `glue.yaml` 分别锁住。智能体、人和流水线读的是同一份文本、同一份校验和。

做成一个统一插件，是把规则、目录、文档和样板收进同一次安装。规则变成插件里的一份副本。插件一更新，正在做的需求所遵守的门禁会跟着变，仓库里的提交看不出变的是哪几句。流水线没有这个图形插件，合入检查就得再写一套，两套会分开走。Cursor 和别的环境还要各做一个插件，规则又多一份副本。

做成 DSH 插件，指的是把这套能力做成插件，挂到插件宿主上，别的组安装之后就能用。安装本身省了一步，但使用方拿到的仍是宿主里的那一版插件，不是仓库里锁住的那一版文本。评审看到的是「装了某个插件」，看不到本次编码读的是哪一版 `工程规约.md`。宿主升级插件，效果和统一插件一样，在途需求的门禁会悄悄换掉。本文不依赖 DSH 的私有接口。比的就是「安装插件即可使用」这一种交付。

打成一个整包，是把流程包、整份目录、全部组件文档和全部样板一次性拷进使用方仓库。文档正文进了业务仓，就会过期，也会进上下文。各组仓库里会出现一份被人改过的规则，提供方发下一版时对不齐。目录和样板的体积、权限也跟业务代码混在一起。

三件发布物避免这三件事。流程包是可 diff 的文本，版本写在 `glue.yaml`。目录只留元数据，文档和样板按程序设计点名的版本现拉。MCP 只负责这几次读取，并且每次留审计。流水线和智能体共用 `glue-init --check` 与 `glue-gate`，不依赖某个编辑器是否装了插件。
