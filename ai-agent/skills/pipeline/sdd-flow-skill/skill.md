# 流水线 Skill

## 何时用

- 用户给出一句话或一段新诉求
- 上一阶段评估刚结束，需要决定下一份文档
- 测试或设计打回，需要决定从哪一段重做

## 步骤

1. 读 `ai-agent/rules/工程规约.md`。
2. 没有需求项编号时，只向用户索取编号。不创建 spec，不写代码。
3. 查看 `ai-agent/spec/{需求项编号}/` 里已有文档和各阶段 `eval.md` 结论。
4. 按下表确定下一阶段。人尚未同意进入之前，不打开下一份 `agent.md`。同意之后只打开那一份，并加载该阶段 `rules/`。

| 当前事实 | 打开 |
|---|---|
| 没有通过的需求用例，或需求确认不是通过 | `01_需求智能体/template/agent.md` |
| 需求已确认，没有通过的概要设计 | 概要设计；测试设计可同时进行 |
| 概要自检已通过，架构师确认不是通过 | 停在 `01_概要设计/rules/架构师确认规约.md` |
| 概要已确认，详细未通过 | `02_详细设计` |
| 详细设计的字段、状态、异常码或处理顺序已变，程序设计未重写 | `03_程序设计` |
| 详细已通过，程序未通过 | `03_程序设计` |
| 程序已通过，编码未通过 | `03_编码智能体` |
| 程序设计已作废，或写明编码须停止 | 停在 `03_程序设计`，不改代码 |
| 编码已通过，P0 未执行完 | `04_测试智能体` 的执行步骤 |
| P0 已完成且失败项已关闭 | `skills/delivery/split-submit-skill/skill.md` |
| 已有用例上的缺陷 | 编码或测试，不重走概要设计 |

5. 阻塞设计的「待确认」未关闭时，停在提出该问题的阶段。
6. 一次会话只推进到当前阶段的完成定义。不在同一轮里把概要、详细、程序和代码一起写完。
7. 已命名写入位置已有改动、准备继续编码时，先按 `工程规约.md` 第 6 节做漂移分类。代理不得代人分类。未分类则不改代码，也不把编码评估写成通过。

## 进入下一阶段

本阶段写完并且 `eval.md` 否决项清零后：

1. 离开本阶段仍要人确认时，确认栏保持待确认并停住。告诉人该由谁签署。代理不得自己写成通过。只有人明确说「确认通过」时，才把这句话记入确认栏。
2. 确认栏还不是通过时，不问是否进入下一阶段，也不打开下一份 `agent.md`。
3. 确认已经是通过，而人还没同意进入下一阶段时，只问一句，然后停住。

| 刚刚通过的确认 | 询问 |
|---|---|
| 需求确认 | 进入概要设计，还是测试设计 |
| 架构师确认 | 是否进入详细设计 |
| 详细设计评估 | 是否进入程序设计 |
| 程序设计评估，且版本锁定已由人确认 | 是否进入编码 |
| 程序设计评估，版本锁定尚未由人确认 | 不询问进入编码，说明版本锁定仍待人确认 |
| 编码评估 | 是否进入测试执行 |
| 测试执行完成，P0 有结果且失败项已关闭 | 是否进入分提 |

4. 人同意，或在同一句话里点名了上表中的阶段之后，只打开那一份 `agent.md`，并且这一轮只做该阶段。
5. 人在对话外改了确认栏时，技能不会自己发现。人回到该需求并说继续之后，再读文档。确认已是通过，才按上表提问。

## 禁止

- 不因为诉求很短就跳过需求用例。
- 不在程序设计写明目标库和写入目录之前改 `git-repo-*` 或 `work/`。
- 不在测试执行完成之前分提。
- 不在人同意进入之前打开下一阶段。
- 不把代理自己的自检写成需求确认或架构师确认。
