# 程序设计 Skill

企业规格驱动在这一阶段把契约变成可编码、可先失败再实现的方案。产物用程序设计模板，不另写 tasks 或 plan 文件，不在本阶段改 `git-repo-*` 或 `work/`。

一个子条目就是一条可以单独验证的竖切，不按「先写完全部类、再写完全部方法」横着拆。

## 何时用

详细设计 `eval.md` 已通过，需要交给编码时。编码发现目标库、路径或失败返回不清时，回到本技能改同一份程序设计。

## 步骤

1. **只读上游。** 读详细设计、工程规范和已经检出的 `git-repo-*`。详细设计未通过，或其中阻塞程序设计的待确认还在时，停止。
2. **定一个库。** 每个子条目一个目标代码库、一个写入目录。映射不在应用规约里就问用户，不自造库名。仓未检出时写 `work/{需求项编号}/{目标库}/`，并标明分层尚未对照。
3. **按类型写。** 技术变更只写版本、证明和回退，类和方法写「不适用」。业务子条目写类或模块、方法级调用链、与异常码一致的失败返回。先列被依赖的方法，P0 行为放在编码顺序前面。
4. **复用优先。** 应用规约点名的公共方法必须复用。要改签名就停，不在这里改契约。
5. **日志和事务。** 应用规约没写时记「待对照」或「无」，不编造注解和字段。
6. **验证写进行为。** 每个 P0 行为一行：先写的失败测试应证明什么。不写测试代码。有既有资产时，验证还要覆盖资产成功和资产失败。资产内部测试不算本服务的验证。
7. **锁定人确认的版本。** 没有候选、或完成方式是本服务实现时，写「资产锁定不适用」。有候选时调用见 `ai-agent/mcp/glue.md`。
   - 调用 `get_component`，带上详细设计已经绑定的标识和人准备锁定的版本。服务不挑选较新版本。
   - `upgrade_existing` 用代码库里已有标识点查，不调用 `search_components`。该版本 `apiCompatibility` 为 `breaking` 时，再调用 `get_doc_section` 只读 `migrationDocChapter`。人看过迁移章之后才能确认。
   - 写下标识、显式版本、文档位置、样例标记、相对样例还要写的差异。不写范围版本，不写 SNAPSHOT。样例标记必须等于该版本，且 `sampleTestsPassed` 为真，编码才允许取文件。发布标识为空则不得锁定。
   - 父工程的版本管理会改掉这个显式版本时，编码前停住问人。确认后不得自动换成更新的版本。
   - 一次选用不回写应用规约的「必须复用」。公共用法变化则锁定作废并停止。仅内部变化且公共用法不变时，另开子项，目标改为资产所在工程。
8. **自检后停止。** `eval.md` 否决项清零才交给编码。人确认锁定之前不得编码。详细设计契约已变时，先整份重写再自检。

## 停止

- 一个子条目要改两个目标库。
- 失败返回在详细设计里没有对应异常码。
- 分层在工程规范、应用规约和已检出的仓里都对不上。
