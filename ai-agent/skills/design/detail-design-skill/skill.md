# 详细设计 Skill

企业规格驱动在这一阶段把概要边界落成可追溯的契约。产物用详细设计模板，不另写接口规格文件，不把字段提前写回概要设计。

借鉴接口设计的两处做法：契约先于实现；重复提交会多写事实时，幂等键和再次提交的结果一起写，只接受键不算契约。

## 何时用

概要设计已经由架构师确认通过，需要拆子条目时。程序设计发现字段、状态或异常码不够写方法时，回到本技能改同一份详细设计。

## 步骤

1. **核对上游。** 需求确认和架构师确认都不是通过时，停止。阻塞设计的待确认还在时，打回提出该问题的阶段。
2. **按服务拆。** 一个子条目只属于一个概要模块、一个服务。跨服务拆成两个子条目，提供方拥有字段表。编号按应用规约取；没写明就问用户，不编造。
3. **按类型写。** 技术变更按目标代码库各写一份，契约各节写「不适用」，只保留该库的证明方式和回退。业务子条目写字段、状态、重复提交的结果、处理步骤和异常码。没有状态或不会多写事实时，对应节写「不适用」。
4. **图只补顺序。** 步骤有分支才加流程图。多个调用且调用方能看见中间失败才加时序图。不重画概要的调用方向图，不画类和方法，不另存图片。
5. **P0 必须有人接。** 用例里的 P0 要落到某个子条目。放进「不包含」时写上承接的子条目编号。
6. **边界冲突就停。** 服务、调用方向、数据归属和概要不一致时，打回概要设计，不在契约里改边界。
7. **只绑定概要已经记下的标识。** 调用见 `ai-agent/mcp/glue.md`。
   - 用概要留下的标识调用 `search_components` 做点查。与概要矛盾则回到概要，不在这里改选。
   - 调用 `get_component`。人未指定版本时只看身份和版本列表。人指定版本后，才看发布标识、样例是否通过、章节标题。发布标识为空的版本不得留到程序设计去锁。
   - 人指定一章后，调用 `get_doc_section` 只读这一章。不得把多个候选的正文都拉下来再挑。
   - 既有资产：证据是读到的文档名称和章节，资产名来自该页。本服务实现：该能力的查阅确实是零命中，证据写「无」。未查阅不得写成「无」。
   - `upgrade_existing` 仍不按能力检索。版本落在程序设计。
8. **自检后停止。** `eval.md` 否决项清零才交给程序设计。契约改了而程序设计已存在时，声明该程序设计作废。

## 停止

- 子条目编号未知。
- 异常码在应用规约和数据架构里都不存在，又没有标成阻塞程序设计的待确认。
- 准备在详细设计里写代码路径或语言代码。
