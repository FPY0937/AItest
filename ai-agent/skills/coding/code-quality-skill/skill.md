# 代码质量 Skill

设计符不符合，由 `code-review-skill` 看。本技能只看这次改动的代码会不会出错、会不会伤到调用方。两个技能都跑完，两边的 Critical 都清零，编码记录才能写成可交付。

清单来自已归档的上游原文，见 `archive/README.md`。不安装 `ocr`，不建知识图谱，不调用那些工具名。

## 何时用

编码智能体完成一个子条目、与 `code-review-skill` 同一次审查。对象是程序设计点名的 `git-repo-*` 或 `work/{需求项编号}/{目标库}/` 里的本次 diff。

## 步骤

1. **圈定文件。** 在该写入目录执行 `git diff HEAD` 看已跟踪文件的改动。未跟踪的新文件直接读全文。只审查这些文件。生成物、锁文件、纯格式化不审查。
2. **按文件类型套清单。** `.java` 用下文「Java」。`*Mapper.xml`、`*Dao.xml` 用「MyBatis XML」。`pom.xml` 里新增的依赖用「构建版本」。其他语言沿用该仓已有写法，仍执行「影响面」。
3. **看影响面。** 对每个被改的对外方法，在本库里搜索直接调用处。看调用方是否还能编译，失败行为有没有被静默改掉。再看对应测试有没有执行到这次改动的分支。调用方看不全时记一条 Suggestion，不编造调用方，也不为此读完整个仓。
4. **写入编码记录。** 每条写明文件、问题、类别（缺陷 / 安全 / 性能 / 可维护 / 测试）。Critical 必须改完。

证据不足就不要报。看不清执行上下文时放过，不把疑似问题写成 Critical。

## Java

来源：`archive/open-code-review/java.md`。

**缺陷，记 Critical**

- 设计要求成功的路径上会出现空指针。先顺着数据从哪来确认，不能只因为有一次解引用就报。
- 条件永远进不去的分支、return 之后的代码、声明后从未读取的变量。大段注释掉的代码记 Suggestion。
- 条件写反、下标和长度的边界错误、布尔运算优先级或短路与意图不符。
- 明显的死循环，或递归没有终止条件。
- switch 缺少 break 而掉进错误分支。有意穿透但没有注释，记 Suggestion。
- return、break、continue 用在了不该离开的位置。

**线程，只在有证据时记 Critical**

- 先检查再动作，中间状态可能被别的线程改掉。
- 多步写入需要原子性，却没有同步。
- 单例或缓存的双重检查锁写错。
- 多线程里改 ArrayList、HashMap 这类非线程安全集合。

下面这些不报：方法内局部变量、没有多线程调用证据、只读、不可变对象、已经用了 synchronized / Lock / 原子类、Builder 组装阶段或只在单线程使用的对象。

**性能，记 Suggestion**

- 循环里访问数据库。先确认那个调用确实会查库。
- 可以一次批量查完，却成了 N+1。
- 大结果集没有分页。
- 嵌套循环是 O(n²) 或更高，并且存在更直接的写法。

**不报的拼写**

- 只在声明处看变量、方法、类名和日志、异常文案里影响阅读的拼写错误，记 Nice to have。引用处的名字由声明决定，不报。

## MyBatis XML

来源：`archive/open-code-review/mapper_dao_xml.md`。

**安全，记 Critical**

- 用 `${}` 把用户输入拼进 SQL。
- LIKE 条件用拼接，而不是参数绑定。

`#{}` 绑定和没有动态参数的固定 SQL 不报。

**逻辑，记 Critical**

- WHERE 里 AND / OR 用反。
- JOIN 字段错了，或少了必要的连接条件。
- `<if test="">` 的空判断或类型判断是错的。
- 缺逗号、括号不配对这类语法错误。
- Mapper 接口方法名和 XML 的 `id` 对不上。

**性能，记 Suggestion**

- 没有 WHERE，存在全表扫描。
- 可能返回大量行，却没有 LIMIT 或分页。
- 同一子查询重复出现。

上下文不够、无法确定这条 SQL 会怎么跑时，不报。

## 构建版本

来源：`archive/open-code-review/pom_xml.md`。

本次新增的依赖版本里出现 SNAPSHOT，记 Suggestion。父 POM 管理版本、本行没有写版本号时，不报。没有改动的旧版本不报。

## 影响面

来源：`archive/code-review-graph/review-pr-SKILL.md` 与 `review-changes-SKILL.md`。不调用其中的图谱工具。

对每个被改的对外方法写出三行，放进编码记录：

- 改了什么。
- 本库里谁直接调用它。没有调用方就写「本库无直接调用方」。
- 测试有没有打到这次改动的分支。没有则记 Suggestion；因此会让调用方走错或无法编译时，记 Critical。

先读改动最大的文件和它的测试，不把未改文件整篇读完。

## 技术变更

没有新的业务代码时，只看 `pom.xml` 或其他构建文件里新增的版本，以及有没有把无关依赖一起改掉。不对未改的业务类做上面的 Java 和 SQL 清单。

## 反馈

- Critical：必须改完，编码评估不得通过
- Suggestion：写进编码记录，不挡住本次交付
- Nice to have：不阻塞
