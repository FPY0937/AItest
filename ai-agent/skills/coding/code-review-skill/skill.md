# 代码审查 Skill

## 何时用

编码智能体完成一个子条目、写入编码记录之前。审查对象是该子条目程序设计点名的 `git-repo-*` 或 `work/{需求项编号}/{目标库}/`。

## 审查范围

只看这次 diff 是否偏离程序设计、详细设计和 `编码公共规约.md`。代码会不会出错、会不会伤到调用方，由并行的 `code-quality-skill` 看。不审查没有点名的仓，也不把审查写成一份新的设计。

## 检查单

- [ ] 方法契约和异常码是否与程序设计、详细设计一致
- [ ] 是否只改了点名的写入目录
- [ ] 是否把业务代码写进了 `ai-agent/` 或 `docs/`
- [ ] 是否改了范围外模块、公共方法签名，或程序设计没有要求的依赖
- [ ] 技术变更是否新增了写成「不适用」的业务类
- [ ] 失败路径是否还在，有没有吞掉异常
- [ ] 是否无关重构或整文件格式化
- [ ] 是否有密钥、硬编码环境地址
- [ ] 分层和命名是否沿用该仓
- [ ] 本次新增或修改的有行为的类是否各有一个测试类，本次改动的每个对外方法是否有成功和失败的测试方法。技术变更没有新业务类时，是否多建了业务测试类
- [ ] 每条 P0 是否有先失败、后通过的命令结果；技术变更是否有既有套件或构建的实际结果
- [ ] 是否用一个已经通过的测试代替先失败的证明
- [ ] 是否重写了程序设计已点名的资产。重写为 Critical
- [ ] 依赖声明是否仍是人确认的显式版本。范围版本、SNAPSHOT，或被父工程改掉却未询问，为 Critical
- [ ] 复制的样例是否只来自样例测试已通过、且样例标记等于锁定版本的文件
- [ ] 有锁定资产时，本服务测试是否覆盖资产成功和资产失败
- [ ] 准备写成可交付，或准备在已有改动上继续编码时，漂移是否已由人分类。未分类为 Critical。代理不得代为分类

## 反馈格式

- Critical：必须改完再把编码记录的结论写成可交付
- Suggestion：可随后改，需写进编码记录
- Nice to have：不阻塞

Critical 未清零时，编码评估不得通过。
