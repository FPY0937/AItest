# 测试驱动 Skill

## 何时用

- 程序设计的验证表要求先写失败测试
- 测试智能体打回缺陷，且契约没有变化

本技能证明该写入目录里的代码符合这一份程序设计。写入目录是 `git-repo-*`，仓尚未检出时是 `work/{需求项编号}/{目标库}/`。它不替代测试智能体的验收用例。

## 步骤

1. 确认程序设计评估已通过，且没有作废或停止编码的标记。有待锁定资产时，人已确认锁定。写明「资产锁定不适用」的，不取样例。一次只取一片行为，P0 在前。已有改动上继续编码之前，先由人按工程规约做漂移分类。未分类则不改代码。
2. 在该写入目录发现验证命令。优先用 `编码应用规约.md` 已写的命令，其次用目录里的构建文件。发现不了就停止，不套用别的仓的命令。
3. 先写测试，运行它，确认失败。失败原因应是行为还不存在，而不是测试本身写错。有行为的类使用同一个测试类：Java 仓放在 `src/test/java` 的同包路径，类名加 `Test`。仓里已有别的测试目录时沿用该仓。本次改动的每个对外方法，在这个测试类里写成功和失败的测试方法。一个方法不另建测试类。只装数据的类不建测试类。
4. 写刚好让这一个测试通过的实现，并带上该片的失败路径。异常码用详细设计已有的码。不提前做下一片。有锁定资产时，按锁定章节调用 `get_doc_section` 只作对照，再调用 `get_sample`。先取文件清单，再按路径取文件。只复制样例测试已经通过、且样例标记等于锁定版本的文件。只编写程序设计写下的、相对样例还要写的那部分。发布标识写入依赖声明，用现有仓库凭证取包，不用 `GLUE_TOKEN`。调用见 `ai-agent/mcp/glue.md`。本服务的测试要覆盖资产成功和资产失败。样例自身的测试通过不算本服务通过。
5. 再跑这一测试，确认通过。然后跑该目录的全量测试和编译。
6. 把先失败和后通过的命令结果写入该子条目的编码记录。全量通过后才把这一片视为完成。

技术变更的验证表若写的是既有测试或构建仍通过：不新造业务测试，跑点名的命令并记录结果。验证表若要求先写失败测试，仍走上面的 3 到 6。

## 缺陷

不改范围、验收、优先级和影响服务的缺陷，留在本技能修复。先写一个能复现该缺陷的失败测试，再改程序设计指定的写入目录，再看它变绿，最后跑全量。禁止先改代码再补一个已经会通过的测试。

## 停止条件

- 测试无法写成失败：程序设计的验证说明不清，打回程序设计。
- 命令跑不了：编码记录里写阻塞。P0 被阻塞时，编码评估不得通过。
- 为了通过测试需要改需求、字段、异常码或公共方法签名：停止，退回对应阶段。
- 程序设计已作废或写明编码须停止：不改代码。
