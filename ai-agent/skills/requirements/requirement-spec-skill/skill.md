# 需求用例 Skill

企业规格驱动在这一阶段只做三件事：组织基线不能被单份用例改写，每条用例有稳定编号并能验收，确认通过后才允许设计。产物仍用需求用例模板，不另写 SPEC.md，不另建追踪矩阵。

## 何时用

需求智能体接到一句话或一段原始诉求时。概要设计发现用例太薄、范围或验收变了时，回到本技能改同一份用例。

## 步骤

1. **先读基线。** 读 `工程规约.md` 和 `需求应用规约.md`。应用规约里已经写明的术语、不可破规则、编号来源，直接遵守。没写的条款向用户索取，不编造，也不把空表当成事实。
2. **要编号和来源。** 没有需求项编号就停止。来源写用户本次输入，或应用规约所指的工单。没有工单号就不编造。
3. **一次只问一个缺口。** 只问会让 `eval.md` 否决项无法清零的问题，并带上默认假设。用户不纠正的，写入「待确认」，标明是否阻塞设计。
4. **按类型写用例。** 业务需求按用户目标拆 UC，每条只有一个主成功目标，并标 P0 或 P1。整份文档至少一条 P0。技术变更不编造角色和业务主流程，验收写行为如何保持，异常只写回退，该验收标 P0。
5. **同一份文档不得自相矛盾。** UC 之间、UC 与范围外、用例与应用规约里已写明的不可破规则，不能互相否定。
6. **修订改原文件。** 同一需求项只保留一份用例。后一次修改在变更记录追加一行。范围、验收、优先级或影响的服务变了，且概要设计已存在时，把概要设计的架构师确认改回待确认。不改这些内容的缺陷，不回头改概要设计。
7. **不选定资产。** 不写组件标识，不写发布坐标，不调用 glue。可复用资产留到概要设计按意图查阅。
8. **自检后停止。** 否决项清零后，需求确认写成待确认，交给确认人。确认人未写入应用规约时向用户索取。智能体自己不算确认人。确认通过之前不写概要设计，也不写测试设计。

## 停止

- 编号未知。
- 阻塞设计的待确认还在，却准备把需求确认写成通过。
- 用例要打破应用规约里已经写明的规则。先问用户，不在用例里悄悄改规则。
