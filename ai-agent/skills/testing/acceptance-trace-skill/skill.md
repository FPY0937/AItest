# 验收追溯 Skill

## 何时用

需求确认为通过，开始写测试设计时。需求的范围、验收或优先级变了，回到本技能改同一份测试设计。

## 步骤

1. 确认需求确认的结论是通过。不是通过就停止。
2. 从需求用例抄出每一条验收，保留 UC 编号和该 UC 的优先级。不改写业务规则，不把 P1 改成 P0。
3. 技术变更只抄「行为保持」和「回退」。不编造角色和业务主流程。
4. 填追溯表：验收项、UC、测试用例 ID、优先级。每一条验收至少一行。用例里的每条 P0 都必须有测试用例 ID。
5. 业务需求为 P0 补上可执行的主成功。权限、边界、失败、重复提交各自有用例。技术变更的 P0 是行为保持和回退。
6. 追溯表有空行，或某条 P0 验收没有用例 ID：停止。缺的是需求原文，就打回需求智能体。不自己补一条业务规则把表填满。
7. 步骤写到角色、入口、关键数据和可判定期望。类名、方法名和 `*Test` 不写入验收。
8. 不调用 glue。资产内部测试不写入本服务验收。需求里已经写明的、资产成功或资产失败时本服务应有的验收，仍按原文追溯。不从组件手册补一条验收。

## 完成

设计阶段可以结束。编码未通过时，不把这一步写成测试完成，也不到 `git-repo-*` 或 `work/` 里发明新的业务验收。
