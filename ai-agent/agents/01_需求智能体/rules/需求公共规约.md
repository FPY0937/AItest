# 需求公共规约

适用于所有应用的需求阶段。组织级规则在 `工程规约.md`，应用级规则在 `需求应用规约.md`。单份用例不能改写这两层里已经写明的内容。

## 1. 目标

把一句话或一段原始诉求变成 **可开发、可设计、可测试** 的需求用例。需求用例是后面所有阶段的事实源。UC 编号是追踪键，不另建追踪矩阵。用例写做什么、为什么，不写实现方案。不选定可复用资产，不写组件标识，不写发布坐标，不调用 glue。

## 2. 必读顺序

1. `ai-agent/rules/工程规约.md`
2. 本文件与 `需求应用规约.md`
3. `docs/应用架构.md`、`docs/工程概述.md`
4. 相关 `docs/功能模块/`、`docs/业务知识/`
5. 若是变更：`ai-agent/spec/` 或 `archive/` 中的既有用例

## 3. 一句话进入

原始诉求通常只有一句话。按这个顺序补齐，缺了就停：

1. 需求项编号。未知则向用户索取，禁止编造，禁止先写文档占位。
2. 成功时长什么样。不能从一句话里推断成已确认的业务规则。
3. 范围内和范围外。
4. 至少一条可判定验收。
5. 影响的服务或模块。对照 `docs/应用架构.md`，对不上就标待确认。

一次只问一个会卡住 `eval.md` 否决项的问题。问的时候带上当前默认假设，用户不纠正才写入「待确认」。能用默认假设推进、且不阻塞设计的，不反复追问。

## 3.1 技术变更

升级依赖、运行时或构建方式，且不新增用户能感知的业务能力时，不按业务用例要求角色和主流程。改为写清：

- 范围内：哪些代码库，以及依赖或运行时从哪一版到哪一版
- 范围外：不改业务规则；不改变返回、错误、时序和默认配置
- 验收：现有行为保持。允许变化的行为逐条列出，不能写「基本兼容」
- 失败路径：如何回退到旧版本
- 影响：落到 `docs/应用架构.md` 中的服务，并写明代码库

返回、错误、时序或默认配置会变化时，按业务需求写用例，并在概要设计中走结构变更。技术变更可以只写一条验收，仍然要可测试。

## 4. 范围纪律

- 必须同时写清 **范围内** 与 **范围外**。
- 禁止把实现方案写进需求（不规定表结构、类名、接口路径、目标库目录），除非它本身就是业务约束。技术变更允许写依赖名和版本，这是验收对象，不是实现方案。
- 禁止把未确认事项写成既定规则；单独列入「待确认」。
- 禁止模糊词充当结论：相关、等、视情况、适当、原则上。

## 5. 用例质量

业务需求的每条用例至少包含：

- 触发角色与前置条件
- 主成功流程（编号步骤）
- 扩展/异常流程
- 可判定的验收标准（Given-When-Then 或等价检查项）
- 影响的应用/服务/功能模块（对照 `docs/应用架构.md`）

每条用例只有一个主成功目标。按用户目标拆，不按技术接口拆。技术变更不适用角色和业务主流程，改用第 3.1 节的版本、行为保持和回退。

每条 UC 标注优先级。P0 是分提前必须有测试结果的验收，P1 可以随后补。一份用例至少有一条 P0。技术变更那条「行为保持」标为 P0。

同一份用例里，UC 之间、UC 与范围外不得互相否定。用例不得打破 `需求应用规约.md` 里已经写明的不可破规则。该节为空时不编造规则。

`需求应用规约.md` 的「合规与数据」已有内容时，非功能节逐条写适用或不适用。该节为空时，非功能写「无」，不编造指标。

## 6. 追踪与变更

同一需求项只保留一份用例主文档，修订时改原文件，并在变更记录追加一行：日期、改了什么、是否影响已有概要设计。

范围、验收、优先级或影响的服务发生变化，且概要设计已存在时，该概要设计的架构师确认回到待确认，详细设计停止。不改这些内容的缺陷，不回头改概要设计。

阻塞设计的待确认未关闭时，需求确认不得写成通过。

## 7. 需求确认

确认人写在 `需求应用规约.md`。该节为空时向用户索取，不编造姓名，也不把智能体自己写成确认人。

`eval.md` 否决项清零后，确认结论写「待确认」。结论为「通过」后，才能进入概要设计和测试设计。打回时只改被点名的内容，改完重新自检、重新确认。

## 8. 落盘

- 工作目录：`ai-agent/spec/{需求项编号}/`
- 文件名：`{需求项编号}_需求用例_{短标题}.md`
- 一个需求项一份用例主文档。子条目由详细设计拆分，编号以 `5` 开头，需求主文档保持总览。
- 需求确认写在同一份文档末尾，不另建审批文件。
