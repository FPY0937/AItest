# 需求用例评估

## 评估对象

`ai-agent/spec/{需求项编号}/{需求项编号}_需求用例_{短标题}.md`

## 否决项（有一条即不通过）

- [ ] 需求项编号不是用户给出的，或文件名与编号不符
- [ ] 没有范围内/范围外
- [ ] 没有可判定的验收标准
- [ ] 业务需求的主流程不可执行（缺角色、缺触发、缺结果）。技术变更改为：没有版本范围或没有回退步骤
- [ ] 业务需求无异常/失败路径。技术变更改为：未写明对外行为是否保持
- [ ] 影响模块无法对照应用架构解释
- [ ] 存在「等 / 相关 / 视情况」充当规则
- [ ] 把实现方案（表、类、接口路径、代码目录）当成需求正文且并非业务约束
- [ ] 没有 P0，或业务用例的 UC 没有优先级。技术变更的「行为保持」未标 P0
- [ ] 来源缺失，或编造了工单号
- [ ] 同一份用例中，UC、范围外、应用规约里已写明的不可破规则互相否定
- [ ] 阻塞设计的待确认仍在，需求确认却写成通过
- [ ] 写了组件标识或发布坐标，或选定了可复用资产

## 评分（通过线 80）

| 项 | 分 | 标准 |
|---|---|---|
| 目标清晰 | 15 | 问题与成功标准一句话能讲清 |
| 范围完整 | 15 | 正反范围对称，无悄悄扩大 |
| 用例可走查 | 25 | 业务需求：主流程、扩展、异常可逐步演练。技术变更：版本范围、行为是否保持、回退可逐步核对 |
| 验收可测试 | 25 | 每条验收能写成测试用例，且至少一条为 P0 |
| 影响可分工 | 10 | 能指到服务/模块 |
| 待确认受控 | 10 | 有默认假设，标明是否阻塞 |
