# 程序设计公共规约

适用于所有应用的程序设计。组织级规则在 `工程规约.md`，应用级差异在 `程序设计应用规约.md`。单份程序设计不能改写详细设计的字段、异常码和重复提交结果。

## 1. 目标

把已经通过的详细设计翻译成编码能照着写的方案：目标代码库、写入目录、类或模块、方法、调用链、事务、日志，以及每个行为先写什么样的失败测试。

程序设计决定「代码落在哪、方法怎么接上契约、先证明哪一条」。它不改契约，也不改 `git-repo-*` 和 `work/` 里的代码。

## 2. 必读顺序

1. `ai-agent/rules/工程规约.md`
2. 本文件、`程序设计应用规约.md`
3. 同一子条目已通过的详细设计、对应的需求用例和概要设计
4. `docs/工程规范_*.md`、`docs/技术架构.md`
5. 已经检出的 `git-repo-*` 只用来对照分层。没有检出就不假装看过那个仓

执行 `ai-agent/skills/design/program-design-skill/skill.md`。

## 3. 去向

每个子条目只属于一个目标代码库。

- 仓已检出：写入目录是 `git-repo-{库名}/` 下的包或目录。
- 仓未检出，或改动先放在规格库：写入目录是 `work/{需求项编号}/{目标库}/`。
- 应用规约没有该服务的目标库时，向用户确认，不自造库名。
- 两个目标库的文件不写进同一份程序设计。需要改第二个库时，回到详细设计另开子条目。

已有 `git-repo-*` 时按该检出的分层写路径。还没有检出时，分层依据写成「来自工程规范」或「待对照」，不发明应用规约和工程规范都没有的目录。

## 4. 方法怎么接契约

业务子条目的每个方法写明输入、成功返回、失败返回。失败返回必须能对上详细设计的异常码，不另起一套错误。

调用链写方法级顺序，并给出编码顺序：先写被依赖的方法。P0 行为排在前面。

详细设计已有流程图或时序图时，方法调用链要能走完那些分支，不另画一张业务时序图。方法级步骤有分支、编号列表会漏时，可以加一段 mermaid，只画类或方法和调用顺序，不另存图片。

标出必须复用的公共方法。应用规约「必须复用」已有内容时直接沿用。要改公共方法签名时停止，回到详细设计或向用户确认，不在程序设计里改签名。

事务和日志：应用规约已写明的边界和必填字段直接沿用。该节为空时写「待对照」，不编造注解和日志字段。没有事务时写「无」。

## 5. 技术变更

概要和详细设计都是技术变更时，不写业务类和方法。程序设计只写：

- 目标代码库和写入目录
- 依赖、运行时或构建从哪一版到哪一版
- 如何证明行为仍在
- 如何回退

类与模块、调用链、方法契约、事务写「不适用」。日志没有新增字段时写「无」。

## 6. 验证

详细设计里每个 P0 行为，都有一行验证：编码应先写的失败测试要证明什么。跑不了时写阻塞条件，不写成已验证。

验证说明交给编码阶段的 `test-driven-skill`。本阶段不写测试代码，也不运行测试。

## 7. 变更

修订时改原文件，并在变更记录追加一行。

详细设计的字段、状态、异常码或处理顺序已经变化时，本文件作废，按新契约重写，评估通过后才能再编码。

只改写入目录或方法契约、且编码已经开始时，编码停止，直到本文件重新通过评估。

## 8. 落盘

`ai-agent/spec/{需求项编号}/{子条目编号}/{子条目编号}_程序设计_{短标题}.md`

一个子条目一份程序设计，与详细设计放在同一目录。

## 9. 资产锁定

没有候选或完成方式是本服务实现时，写「资产锁定不适用」。有候选时，版本由人指定并确认，写成显式版本。发布标识为空不得锁定。不兼容升级必须先读到迁移章。一次选用不回写应用规约的「必须复用」。人确认锁定之前不得编码。
