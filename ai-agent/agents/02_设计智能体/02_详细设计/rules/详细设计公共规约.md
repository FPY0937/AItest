# 详细设计公共规约

适用于所有应用的详细设计。组织级规则在 `工程规约.md`，应用级差异在 `详细设计应用规约.md`。单份子条目不能改写概要设计已经确认的服务、调用方向和数据归属。

## 1. 目标

在已确认的概要模块内，把子条目写成程序设计不用猜的契约：对象、状态、字段、校验、重复提交的结果、处理步骤、异常码。

详细设计决定「这条契约长什么样、失败时对方看见什么」。它不决定类、方法、表结构和代码路径。

UC 编号和子条目编号是追踪键，不另建追踪矩阵。

## 2. 必读顺序

1. `ai-agent/rules/工程规约.md`
2. 本文件、`详细设计应用规约.md`
3. 需求确认通过的需求用例，以及架构师确认为通过的概要设计
4. `docs/数据架构/`、相关 `docs/功能模块/`
5. 若是修订：同一子条目已有的详细设计和程序设计

## 3. 先看概要属于哪一种

执行 `ai-agent/skills/design/detail-design-skill/skill.md`。

- **技术变更**：按目标代码库拆子条目。每个子条目只记录该库要动的依赖或运行时，以及如何证明行为仍在、如何回退。对象、字段、状态、处理步骤、时序图、流程图、异常码写「不适用」。不编造业务契约。
- **范围内改动**和 **结构变更**：在概要模块内写契约。不新增概要里没有的服务或调用。概要写了「沿用既有，无新增」时，字段表写「沿用既有字段」，只列出本子条目要读或要改的字段，不发明新字段。

一个子条目只落在一个概要模块、一个服务。跨两个服务的契约拆成两个子条目。提供方子条目拥有字段表；消费方只写自己依赖的子条目编号和要用的字段，不复制整张表。

## 4. 契约写到哪一层

业务子条目必须闭合四件事：输入、处理、落库或出站、失败。

- 会留下状态的对象，写出每个状态的进入条件和离开条件。没有状态迁移时写「不适用」，不编造状态机。
- 字段写明必填还是可空、含义、校验。成功和失败路径都要读的字段都要列出。
- 重复提交会多写出一份事实时，写明幂等键和再次提交的结果。读操作或不会多写事实时，幂等键写「不适用」。接受了幂等键却不写再次提交的结果，契约不成立。
- 异常使用稳定的异常码，并写调用方可见结果、能否重试。不写「视情况」。
- 数据变更的归属必须与概要设计一致。归属冲突时打回概要设计，不在这里改归属。

`详细设计应用规约.md` 里已经写明的对象名、状态和异常码直接沿用。该节为空时，不新造一套名字；未知的码写入待确认，阻塞程序设计。

## 5. 图

图不是每个子条目的必填项，也不另存图片。步骤和表是事实源。图和它们不一致时，先改步骤和表。

- **流程图**：处理步骤有条件、循环或部分成功，按编号往下读会漏掉分支时，在步骤后加一段 mermaid。一条直线就能走完的，不画。
- **时序图**：本子条目按顺序调用多个已有模块，并且调用方能看见中间某一步失败时，加一段 mermaid，只画参与者和消息顺序。字段和异常码仍以表为准。一次请求、一次应答，不画。不重画概要设计里那张调用方向图。
- 类、方法、事务和代码路径不画在详细设计里。技术变更两种图都不画。

## 6. 与上下游的边界

子条目编号以 `5` 开头。取号方式见应用规约；未写明时向用户索取，禁止编造。

用例里标成 P0 的 UC，必须被某个子条目承接。写进「不包含」时，要指出承接它的另一个子条目编号。没有承接编号就停止。

改了字段、状态、异常码或处理顺序，且程序设计已存在时，该程序设计作废，编码停止，直到程序设计按新契约重新通过评估。

要改服务、调用方向、数据归属，或把概要里的「兼容」改成「破坏」时，停止并打回概要设计，架构师确认回到待确认。

阻塞程序设计的待确认未关闭时，不得交给程序设计。

## 7. 落盘

`ai-agent/spec/{需求项编号}/{子条目编号}/{子条目编号}_详细设计_{短标题}.md`

一个子条目一份详细设计。修订时改原文件，并在变更记录追加一行。不写具体语言代码，不写 `work/` 或 `git-repo-*` 路径。

## 8. 完成方式

只处理概要已经记下的标识。点查与概要矛盾时回到概要，不在这里改选。既有资产的证据是读到的文档名称和章节。本服务实现只在该能力确实零命中时使用，证据写「无」。未查阅不得写成「无」。人指定一章之前不读正文。版本不在本阶段锁定。
