# 架构师确认规约

概要设计的放行记录。确认人判断服务边界能不能交给详细设计，不代替详细设计写字段，也不代替 `eval.md` 做文档自检。

## 1. 确认人

确认人写在 `概要设计应用规约.md`。该节为空时，向用户索取确认人，不编造姓名，也不把智能体自己写成确认人。

## 2. 何时必须确认

先看概要设计属于哪一种。编写者自己的 `eval.md` 通过不算确认。

**技术变更**（依赖、运行时或构建升级，且对外行为不变）：核对版本范围、涉及的代码库、行为保持的证明和回退。不要求系统级接口。跨多个代码库时确认影响面已经列全。若确认人认为行为会变，打回并要求改成结构变更。

**范围内改动**（只改已有服务，沿用既有调用，数据归属不变；可以是多个服务或多个代码库）：核对模块落在这些服务、主流程能走查、用户能感知的失败已写明。有能力地图时先看地图和构建顺序。留下确认记录即可。跨多个代码库只核对影响面已经列全，不因此升成结构变更。

**结构变更**（新增服务、新的系统间调用、同步或异步变化、数据归属变化，或升级改变了返回、错误、时序、默认配置）先确认能力地图（若有），再按第 4 节逐项看完全文：

- 新增服务，或使用了应用架构里尚未列出的服务
- 新增系统间调用，或改变既有调用的同步/异步
- 数据归属发生转移，或两个服务都要写同一份事实数据
- 失败后的补偿责任落在本次新划入的服务上

## 3. 何时不能确认

- 概要设计 `eval.md` 仍有否决项
- 需求用例里阻塞设计的待确认尚未关闭
- 确认意见要求补充字段、类或表结构。这些退回后仍属于详细设计，不在确认环节补写

## 4. 确认时看什么

| 看的内容 | 通过的标准 |
|---|---|
| 服务 | 每个模块都能在应用架构中找到服务；新服务已被明确接受 |
| 方向 | 依赖和调用都是单向的；互相等待的职责已经合成一个模块 |
| 地图 | 有多块可独立验收的能力时，能力地图已确认，且构建顺序与依赖一致 |
| 取舍 | 新服务、新调用、同步或异步、数据归属写了倾向和放弃的方案 |
| 数据 | 每份事实数据只有一个归属服务 |
| 失败 | 每次跨服务调用都写了调用方看见什么、谁补偿、能否重试 |
| 范围 | 没有超出需求用例的范围内/外；已定事实没有被重写 |
| 层次 | 没有字段、类、方法、表结构和代码路径 |

技术变更不看方向、地图、数据和失败四行，改为核对版本范围、行为是否保持、证明方式和回退。其余类型有一条不成立，结论写「打回」，并写明要改概要设计的哪一节。概要设计改完后重新自检，再确认一次。

## 5. 如何记录

写在概要设计文档末尾，不单独建文件：

```markdown
## 10. 架构师确认
- 结论：待确认 / 通过 / 打回
- 确认人：
- 日期：
- 适用的确认情形：
- 意见：
```

结论为「待确认」或「打回」时，不得开始详细设计。结论为「通过」后，详细设计只在已确认的服务和调用方向内工作。

需求用例的范围、验收、优先级或影响服务变更后，本确认回到待确认。详细设计停止，直到需求重新确认、本确认重新通过。

## 6. 确认之后又要改边界

详细设计、程序设计或编码发现服务归属、调用方向、数据归属与实现不符时，停止向下写，回到概要设计修改，并重新确认。不在下游文档里悄悄改边界。
