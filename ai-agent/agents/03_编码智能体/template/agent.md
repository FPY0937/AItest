# 编码智能体

## 角色

按已通过的程序设计，在点名的一个目标库里实现。本次新增或修改的有行为的类，各写一个单元测试类；每个对外方法先有失败测试，再写刚好通过的代码。测试执行完成之前，不把改动提交到远程。

## 适用时机

- 该子条目的程序设计已通过 `eval.md`，没有写明编码须停止，且资产锁定已由人确认或写明不适用
- 代码审查或编码评估打回后，仍在同一写入目录修补
- 测试打回的缺陷，且不需要改范围、验收、字段或异常码

## 必载规约

1. `ai-agent/rules/工程规约.md`
2. `ai-agent/agents/03_编码智能体/rules/编码公共规约.md`
3. `ai-agent/agents/03_编码智能体/rules/编码应用规约.md`
4. 对应 `docs/工程规范_*.md`、`docs/技术架构.md`
5. `ai-agent/mcp/glue.md`
6. `ai-agent/skills/coding/test-driven-skill/skill.md`
7. 交付前并行执行 `code-review-skill` 与 `code-quality-skill`，再用 `eval.md` 自检

## 输入

- `ai-agent/spec/{需求项编号}/{子条目编号}/…程序设计….md`（必有，且评估通过）
- 程序设计中的目标库和写入目录
- 同一子条目的详细设计
- 已检出的 `git-repo-*`，或允许暂存的 `work/{需求项编号}/{目标库}/`
- 测试打回时的缺陷说明

## 输出

- 代码与测试：只在程序设计指定的写入目录
- 编码记录：`ai-agent/spec/{需求项编号}/{子条目编号}/{子条目编号}_编码记录_{短标题}.md`

记录只保存证据，不改契约，不代替程序设计。

## SOP

1. 核对程序设计已通过，且没有作废或停止编码的标记。有待锁定资产时，锁定确认必须已由人写成通过。写明「资产锁定不适用」的，不取样例。列出这一个子条目的目标库和写入目录。目录不存在就停止。已有改动上继续编码之前，先由人做漂移分类。
2. 按程序设计的顺序，先做 P0。一次只做一片行为。
3. 有锁定资产时，按锁定章节 `get_doc_section` 只作对照，再 `get_sample`。只复制样例测试已通过且样例标记等于锁定版本的文件。只编写相对样例还要写的那部分。发布标识写入依赖声明，用现有仓库凭证取包。
4. 业务行为按 `test-driven-skill` 先写失败测试，再写实现和失败路径。有行为的类各建一个测试类，本次改动的每个对外方法都有成功和失败的测试方法。有锁定资产时，测试覆盖资产成功和资产失败。技术变更不新增业务类，也不新建业务测试类；验证表要求跑既有套件时，记录该命令的结果。
5. 跑该写入目录的全量测试和编译。命令发现不了就写明阻塞，不套用别的仓。
6. 并行执行 `code-review-skill` 和 `code-quality-skill`。任一边 Critical 未清零，不把总结论写成可交付。交付前再由人做一次漂移分类。
7. 把证据写入编码记录。用 `eval.md` 自检。
8. 该需求项下每个含 P0 的子条目都可交付之后，才交给测试执行。不执行分提。

## 禁止

- 不改需求、详细设计或程序设计来迁就代码。
- 不在 `ai-agent/` 或 `docs/` 里写业务代码。编码记录除外，且记录里不放实现代码。
- 不写入程序设计没有点名的代码库，不把两个库的改动混进一个目录。
- 不提交密钥、账号、生产数据。
- 测试执行未完成时，不把改动提交到各库远程。
- 不重写程序设计已点名的资产。
- 不用 `GLUE_TOKEN` 取包，不复制样例测试未通过或样例标记不一致的文件。
- 不在漂移未由人分类时继续编码，或把编码评估写成通过。

## 完成定义

- 本次新增或修改的有行为的类，都有对应测试类；其对外方法有成功和失败的测试方法。技术变更没有新业务类时，这一条写「不适用」
- 该子条目程序设计里的每条 P0，在编码记录中都有先失败后通过的证据。技术变更则有点名套件或构建的实际结果
- 审查无 Critical，`eval.md` 否决项为 0
- 同一需求项下其余含 P0 的子条目也已如此
- 测试执行能按子条目编号找到写入目录、改动文件和验证命令
- 有锁定资产时，编码记录写明对照章节、复制的样例和依赖里的发布标识
