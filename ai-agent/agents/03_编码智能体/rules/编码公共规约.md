# 编码公共规约

适用于所有应用的编码阶段。组织级规则在 `工程规约.md`，应用级差异在 `编码应用规约.md`。代码不能改写程序设计里的方法契约、异常码和目标库。

## 1. 目标

按已通过的程序设计，在点名的写入目录里实现，并用先失败、后通过的测试留下证据。跨多个代码库时，每个子条目只改自己的那一个库。

编码证明程序设计里的行为在该目录里成立。它不替代测试智能体的验收，也不把改动提交到远程。

## 2. 必读顺序

1. `ai-agent/rules/工程规约.md`
2. 本文件与 `编码应用规约.md`
3. 本子条目已通过的程序设计、详细设计；需要时回看需求用例
4. `docs/工程规范_*.md`、`docs/技术架构.md`
5. 程序设计点名的 `git-repo-*`。跨版本时，这里检出的是要改的那个版本
6. `ai-agent/skills/coding/test-driven-skill/skill.md`
7. `ai-agent/skills/coding/code-review-skill/skill.md`
8. `ai-agent/skills/coding/code-quality-skill/skill.md`

## 3. 门禁

- 没有程序设计，或程序设计评估未通过，禁止编码。
- 程序设计的变更记录写明编码须停止，或详细设计已宣布该程序设计作废时，停止。先重写程序设计。
- 程序设计与需求或详细设计冲突时停止，退回对应阶段。禁止在代码里改验收、字段或异常码。
- 应用规约没有该服务的目标库，且程序设计也没有写明时，向用户确认，不自造库名。

## 4. 写到哪里

- 只改程序设计列出的那一个目标库和写入目录。
- 仓已检出：写入 `git-repo-{库名}/`。目录不存在就停止，说明应克隆哪个库、哪个版本。不自行克隆到别的路径。
- 仓未检出：写入 `work/{需求项编号}/{目标库}/`。
- 业务代码不写入 `ai-agent/`、`docs/`，也不写入没有点名的仓。
- 沿用该仓已有分层。应用规约、工程规范和仓里都没有的分层，不新造。
- 禁止无关重构、格式化整个文件、升级依赖，除非程序设计明确要求。
- 程序设计点名的公共方法必须复用。要改签名时停止，回到程序设计。

## 5. 怎么实现

一次只做一个子条目，一次只做该子条目里的一片行为。程序设计把 P0 排在前面，编码也先做 P0。一片的测试还没通过时，不开始下一片。

业务行为按 `test-driven-skill`：先写会失败的测试，确认失败原因是行为还不存在，再写刚好让它通过的实现，并带上程序设计里的失败路径。失败返回使用详细设计的异常码，不另起一套，不吞掉异常。

技术变更不新增程序设计写成「不适用」的业务类和方法。验证表要求「已有测试或构建仍通过」时，跑现有套件并记录结果，不新造业务测试。验证表要求先写失败测试时，仍按测试驱动做。

## 5.1 单元测试

单元测试和业务代码写在同一个写入目录，不写进 `spec/`。

本次新增或修改、并且承担行为的类，各有一个测试类。`OrderService` 对应 `OrderServiceTest`。一个方法不另建一个测试类。只装数据、没有行为的类不建测试类。

Java 仓的测试类放在同一模块的 `src/test/java`，包路径与被测类一致。该仓已经使用别的测试目录时，沿用该仓，不另起一套。应用规约写了测试根目录时，以应用规约为准。

该类本次新增或修改的每个对外方法，至少有一个测试方法覆盖成功，一个覆盖本次会失败的路径。失败路径对上详细设计的异常码。私有方法通过对外方法覆盖，不单独建测试类。

这些测试方法就是程序设计里那一片行为的失败测试：先写测试并确认失败，再写实现。P0 的方法先做。本次没有改到的旧方法不补测试，除非程序设计把它列进验证表。

技术变更不新增业务类时，不新建业务测试类。

验证命令先用 `编码应用规约.md` 已写的命令，否则用该写入目录里的构建文件。发现不了就停止并写明阻塞，不套用别的仓的命令。

日志和事务只使用应用规约或程序设计已经写明的字段和边界。写着「待对照」时，先对照已检出的仓；仓里也没有就停止并提问，不编造注解。

## 6. 证据与审查

每个子条目在规格目录留下一份编码记录，不把记录写成新的设计。记录至少包含：写入目录、改动文件、被测类与测试类的对应、每条 P0 先失败和后通过的命令结果、全量验证结果、审查结论。

按 `code-review-skill` 和 `code-quality-skill` 并行审查本次 diff。任一技能的 Critical 未清零时，编码评估不得通过。

P0 没有先失败后通过的记录时，不得进入测试执行。P0 被阻塞时，编码评估为不通过。P1 可以写明未做和原因，不因此挡住 P0 已经完成的子条目进入测试执行；同一需求项还有未完成的 P0 子条目时，整个需求项仍不进入测试执行。

## 7. 缺陷

已有用例上的缺陷不改范围、验收、优先级和影响服务时，留在编码修复，不重走概要设计。先写能复现该缺陷的失败测试，再改程序设计指定目录里的代码。

修复需要改字段、异常码或公共方法签名时停止，退回详细设计或程序设计。

## 8. 落盘

代码和测试写在程序设计指定的写入目录。

编码记录：`ai-agent/spec/{需求项编号}/{子条目编号}/{子条目编号}_编码记录_{短标题}.md`

一个子条目一份记录。修订时改原文件，并在记录里追加命令结果，不另建一份设计。本阶段不执行分提，不把改动提交到各库远程。

## 9. 资产

人确认锁定之前不取文件。`get_doc_section` 只对照锁定章节。`get_sample` 只取样例测试已通过、且样例标记等于锁定版本的文件。只编写相对样例还要写的那部分。重写已点名资产，审查为阻断级。本服务测试覆盖资产成功和资产失败。样例自身的测试通过不算本服务通过。发布标识用现有仓库凭证写入依赖，不用 `GLUE_TOKEN`。继续编码或把评估写成通过之前，先由人做漂移分类。
