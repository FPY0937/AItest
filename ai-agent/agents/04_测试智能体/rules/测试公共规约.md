# 测试公共规约

适用于所有应用的测试阶段。组织级规则在 `工程规约.md`，环境、账号和造数写在 `测试应用规约.md`。单份测试文档不能改写需求用例里的验收和优先级。

## 1. 目标

证明需求用例中的验收被满足。测试设计回答「测哪条验收、步骤是否能交给别人执行」。测试执行回答「P0 在目标库上的实际结果」。两件事都完成，才叫测试完成。

单元测试由编码写在目标库的测试目录里。本阶段不编写、不代替那些测试类。编码记录里的单元测试通过，不算验收通过。

## 2. 必读顺序

1. `ai-agent/rules/工程规约.md`
2. 本文件与 `测试应用规约.md`
3. `docs/测试概述.md`、相关 `docs/场景测试说明书_*.md`
4. 需求确认通过的需求用例
5. `ai-agent/skills/testing/acceptance-trace-skill/skill.md`
6. 设计阶段按需读概要、详细、程序设计，只用来理解边界，不改写验收原文
7. 执行阶段读各子条目的编码记录，以及其中点名的 `git-repo-*` 或 `work/{需求项编号}/{目标库}/`

## 3. 两段时机

- **测试设计**：需求确认为通过后即可开始，可与概要、详细、程序、编码并行。需求确认不是通过时，不写测试设计。
- **测试执行**：该需求项下每个含 P0 的子条目，编码评估都已通过之后。执行对象是编码记录里的写入目录。

## 4. 设计写什么

执行 `acceptance-trace-skill`。

- 每条验收至少映射一条测试用例。优先级沿用该验收所在 UC 的 P0 或 P1，不把 P1 改成 P0。用例里的每条 P0 验收都必须有测试用例。
- 业务需求要覆盖主成功、权限或角色、边界、异常或失败。用例里写了重复提交时，单独成例。
- 技术变更不编业务主流程和角色。要测的是：现有行为保持，以及如何回退。允许变化的行为只测需求里逐条列出的那些。
- 等价类和边界只使用需求或详细设计里已经写明的规则。详细设计尚未通过时，不发明字段。详细设计通过后，若字段边界会影响某条验收，补进同一份测试设计。
- 步骤写到角色、入口、关键数据和可判定期望。禁止「按正常流程操作」「检查是否正确」。
- 不把类名、方法名、`*Test` 写成业务验收。
- 已有场景测试说明书能覆盖的，引用，不整篇抄进 `docs/`。
- 应用规约里的环境、账号、造数为空时写「待确认」，不编造账号和地址。待确认未关闭时，用例仍要可执行，执行阶段遇到它就记阻塞。

## 5. 执行写什么

- 只跑优先级为 P0 的测试用例。P1 可以随后补，不作为测试完成的条件。
- 每条 P0 记录环境、写入目录、结果、缺陷编号。结果只使用：通过、失败、阻塞。
- 阻塞不是通过，不算测试完成。
- 失败时写下现象、期望、实际、对应 UC、复现数据，打回编码智能体，在原写入目录修改。本阶段不改业务代码，也不改单元测试来让验收变成通过。
- 编码修复后重跑失败的 P0。全部 P0 有结果且失败项已关闭，才算测试执行完成，才可以分提。

范围、验收或优先级变更后，已有测试设计和执行记录作废，按新用例重写。不把旧的「通过」沿用到新验收上。

## 6. 落盘

工作目录：`ai-agent/spec/{需求项编号}/`

| 产物 | 文件名 |
|---|---|
| 测试设计 | `{需求项编号}_测试设计_{短标题}.md` |
| 测试用例 | `{需求项编号}_测试用例_{短标题}.md` |

一个需求项各一份。修订时改原文件，并在变更记录追加一行。执行结果写在测试用例文档末尾，不另建只存在于对话里的结果。

仅当出现可复用的新业务场景时，才增量更新 `docs/场景测试说明书_*.md`。一次性数据和脚本不写入 `docs/`。

## 7. 资产

不调用 glue。资产内部测试不写入本服务验收，也不写成 P0 通过。需求里已经写明的、资产成功或资产失败时的验收，仍按原文执行。
